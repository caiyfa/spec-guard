## 一、背景与现状

### 1.1 SpecGuard 是什么

TDM（干部人才盘点系统）的后端自动化测试流水线，位于 `tests/specguard/`。核心理念：

- **契约驱动**：场景 YAML 双层结构（doc 人读层 given/when/then + flow/verify 机器读层），与 `raw/spec/modules/` 的 Spec FR 编号挂钩；
- **DB 预言（oracle）**：不只断言 HTTP 响应，还把响应与 `tdm_snap_profile`/`tdm_emp_employee`/`dhr_employee` 等真值表逐字段比对（8 个断言器）；
- **权限预言**：实时从 hr-center 抓取账号三维权限范围（corp/groupLevel/vm）作为权限断言的预期真相源；
- **报告 JSON 先行**：`reports/{run_id}/run.json + cases/*.json` 为可视化数据源，MD 只是渲染视图。

当前覆盖：干部全景档案（person-profile）15 个场景，**全部是只读查询型**。

### 1.2 引擎架构现状

```
scenario_loader（YAML→Scenario） → dependency_graph（DAG/循环检测/拓扑序）
    → scenario_runner（flow 步骤调度 + verify 断言 + 实例池 + teardown）
    → report_writer（run.json/cases/report.md）
外围：token_provider（SSO 账号池缓存）/ db_oracle（SELECT-only 守卫）
系统适配：systems/tdm/（工号池 emp_pool / 步骤 steps / 断言器 oracles / 查询库 queries）
```

依赖模型从一开始就是 **DAG**（`depends_on` + 拓扑排序 + 闭包回溯），2026-07-22 之前的复用语义是：**上游 session 内只执行一次，结果无限共享**（`upstream_cache`）。这个语义对只读场景是最优解——正因如此我们当天还修复了"目标场景与上游双跑"的缺陷来强化它。

### 1.3 为什么要做状态管理（设计动因）

**人力系统的本质是工作流推进**：盘点活动 DRAFT→ACTIVE→CLOSED、盘点会话五步法 Step1→5、人员导入→锁定→结果导入→完成。这意味着测试场景库的主体终将是**写型场景**，而写型场景之间存在**状态消耗**关系：

> 上游产出一个 IN_PROGRESS 会话 → 消费者 A 把它推进到 COMPLETED
> → 同样需要 IN_PROGRESS 会话的消费者 B **没得用了**。

"一次执行、无限共享"的缓存模型在这里失效。这不是过度设计的假想——是 TDM 业务形态（盘点五步法状态机、会话退回、历史导入覆盖策略）决定的必然需求。

## 二、设计源起：原始问题与推演过程（历史对话存档）

> 本节完整保留 2026-07-22 的设计对话，供后来者理解每个决策的来龙去脉。

### 2.1 提出者原始洞察（原文）

> "一个完整的场景跑下来应该不是一个线条，而是树状的，而且一个用例跑出来的结果
> 在后续可能会被好几个用例使用，使用过后 那一次跑完的结果就不可用了，
> 所以那一次用例的应该执行多次供后续使用，每个用例应该需要标记
> 是否需要独占某个依赖用例的某个状态的执行结果吧。
> 这样不仅仅是头大脚轻或者头小脚大，而是很复杂的一个用例执行场景"

后续补充（回应"是否过度设计"的质疑）：

> "我思考的并不是过度设计，而是真实存在的。全景档案确实是读场景，
> 但是人力系统是写场景更频繁的，因为人力系统更多的是工作流推进。
> 所以 V2 落地，V3 也落地。"

### 2.2 逐点分析结论

| 原始命题 | 判定 | 说明 |
|----------|------|------|
| 场景执行是树状而非线条 | ✅ 成立 | 引擎本就是 DAG（比树更泛化：支持菱形依赖与汇聚节点） |
| 一个用例结果被多个用例使用 | ✅ 成立，已实现 | `upstream_cache`/实例池 + `{{上游ID.x}}` 跨场景引用 |
| **使用过后结果就不可用** | ⚠️ **需修正** | 只对"变更消费"成立，见 2.3 三分法；一刀切会让只读场景也被迫重跑，效率倒退 |
| 用例应标记是否独占依赖的某个状态 | ✅ 成立 | 即业界 fixture scope / 资源租约（lease）概念 |
| 该用例应执行多次供后续使用 | ⚠️ 是解法之一非唯一解 | 见 2.4 四策略对比，重跑不是首选 |
| 整体是复杂的执行场景 | ✅ 成立且更甚 | 还需实例命名空间绑定、teardown、BLOCKED 传播粒度、并行资源锁 |

### 2.3 关键修正：消费类型三分法

"用完即失效"不是普遍规律，必须区分：

| 消费类型 | 结果是否失效 | 例子 | 正确策略 |
|----------|------------|------|----------|
| **只读消费** | ❌ 永不失效 | 拿 activityId 查档案/九宫格 | 共享缓存（V2 的 shared） |
| **变更消费** | ✅ 消费后失效 | 把 IN_PROGRESS 会话推到 COMPLETED | 独占实例（V2 的 exclusive） |
| **时间性失效** | ⏳ 与消费无关 | token 过期、定时任务改写数据 | TTL/重新获取，非租约问题 |

### 2.4 独占需求的四种满足策略对比

| 策略 | 做法 | 代价/限制 | 结论 |
|------|------|----------|------|
| 预建实例池 | 静态数出独占消费者数 N，上游预跑 N 份 | `-k` 过滤后 N 会变；为可能不跑的用例预付成本 | 暂不做（§六.3 留静态计数钩子） |
| **懒重跑** | 独占消费者到来时才新建一份实例 | 上游须幂等可重复；SIT 会堆积数据（配 teardown 缓解） | **V2 已采用** |
| 借用-归还 | 独占者用完 teardown 恢复原状态 | 需操作可逆；每个写场景配清理钩子 | V2 的 teardown 即此机制的载体 |
| **数据分片** | 独占消费者各用不同数据切片（不同的人/会话），天然无冲突 | 需要测试数据储备 | **最优先手段**，见 §五租约模型 |

**最佳实践排序：数据分片 > 借用-归还 > 懒重跑 > 预建实例池。**
能靠隔离数据解决的，不引入执行次数与状态租约的复杂度。

### 2.5 交付约束

资源有限，分两段交付（2026-07-22 决策）：
- **必要开发**（已完成）：V2 核心 = shared/exclusive 实例语义 + teardown + 报告适配 + 离线自测；
- **其余沉淀为本设计文档**，供后续同事推进（§五起）。

## 三、已完成部分（V2，2026-07-22 落地）

已实现并有离线自测全覆盖（`python -m pytest tests/specguard -k engine_modes -v`，10 个测试，无需网络/DB）：

| 能力 | 实现位置 | 说明 |
|------|----------|------|
| `depends_on` 对象形式 | `engine/scenario_loader.py` `_normalize_depends` | 字符串=shared（兼容现状）；`{id, mode: exclusive}`=独占 |
| 实例池 | `engine/scenario_runner.py` `_Instance`/`_acquire_instance` | shared 复用唯一共享实例；exclusive 懒重跑新建 |
| 实例命名空间绑定 | `_Instance.export_ns` | `{{上游ID.x}}` 绑定到自己那份实例，含传递依赖（世界观一致） |
| 失败隔离 | `_UpstreamFailed` | 独占实例失败只 BLOCK 绑定它的消费者 |
| teardown 钩子 | `run_teardowns()`（conftest 落盘前调用） | LIFO、实例变量插值、失败仅记 trace 不改 verdict |
| `produces` 声明 | loader 校验 + record.given 落盘 | 目前仅文档化/报告展示，调度器尚未消费（§六） |
| 多实例报告 | `engine/report_writer.py` | `cases/{id}_inst{n}.json`、run.json 含 `instance_no`/`dep_mode` |
| 无 teardown 告警 | `engine/dependency_graph.py` | 被独占消费但无 teardown → 加载期 WARN |

**设计决策记录**（实施 V3 时不要推翻，除非有新证据）：

1. **独占 = 懒重跑，而非预建实例池**：只在独占消费者真正到来时才重跑，避免为 `-k` 过滤掉的用例预付成本。
2. **exclusive 永不触碰共享实例**：无法预知后续是否还有 shared 消费者，宁可多跑一份也不污染共享世界观。
3. **独占实例的变量不发布到全局 `shared_ns`**：只进绑定消费者的 `export_ns`，防止实例串味。
4. **teardown 失败不改 verdict**：清理尽力而为，测试结论以 flow+verify 为准。

## 四、统一租约模型 —— 回应"工号池独占是否狭隘"

### 4.1 直面问题

**问：为什么是工号池独占？其他数据甚至一个用例是否都可能成为独占租约的一部分？工号池独占租约是否狭隘了？**

**答：狭隘了。租约（lease）是通用模型，工号池只是它在 TDM 的第一个接入点，不是模型边界。**
事实上 **V2 已实现的 `mode: exclusive` 本质就是租约**——租的对象是"一个场景的一次执行实例及其产出状态"。所以"一个用例成为独占租约的一部分"不是未来设想，是已落地的现实。本节把完整模型摆出来，避免后来者被"工号池"三个字带偏。

### 4.2 租约对象全景：什么都可以被租，按层分类

**判定原则**：一个东西该成为租约对象，当且仅当同时满足——
① 被多个场景争抢；② 使用会改变其状态或互斥（不能并存使用）。
只满足①不满足②的（如只读查询同一个人）不需要租约。

| 层 | 租约对象 | TDM 实例 | 满足策略 | 状态 |
|----|----------|----------|----------|------|
| **场景实例层** | 一次执行的产出状态 | exclusive 依赖：独占一份 IN_PROGRESS 会话实例 | 懒重跑新建实例 | ✅ V2 已实现 |
| **数据实体层** | 业务数据行 | 工号、会话 ID、活动 ID、导入批次 | 数据分片（池内不重复分配） | §五 待实施 |
| **账号层** | 测试身份 | AD 账号（Authing 对同账号并发 signin 有风控；某些操作按操作人幂等） | 账号池分配 + 归还 | §五 同一注册表支持 |
| **环境配置层** | 全局唯一、不可复制的配置 | 下拉配置项、导入映射配置、系统开关 | **无法分片/重跑复制** → 只能串行借用-归还（独占期间加锁 + teardown 恢复原值） | §六 调度器阶段 |

四层的本质区别在于**可复制性**：
- 场景实例层可复制（再跑一遍就是新的一份）→ 懒重跑；
- 数据实体层可分片（池里换一个人）→ 租约注册表；
- 环境配置层**不可复制也不可分片**（全系统就一份下拉配置）→ 只能时间上互斥（借用-归还），这是将来并行化的硬约束点。

### 4.3 统一抽象：LeaseRegistry（通用租约注册表）

不为工号单独造轮子，一开始就落通用注册表，工号池只是第一个 `resource_type`：

```python
# engine/scenario_runner.py — RunContext 新增
class LeaseRegistry:
    """session 级资源租约注册表。任何步骤处理器/调度器都可接入。

    resource_type: 资源类型标识（emp_no / session_id / account / config_key / ...）
    key:           资源实例标识
    holder:        持有者（场景 ID + 实例号），用于报告展示与冲突诊断
    """
    def __init__(self):
        self._leases = {}   # {resource_type: {key: holder}}

    def acquire(self, resource_type, key, holder):
        held = self._leases.setdefault(resource_type, {})
        if key in held:
            return False          # 已被租出，调用方决定换候选还是 SKIP
        held[key] = holder
        return True

    def leased_keys(self, resource_type):
        return set(self._leases.get(resource_type, {}))

    def release(self, resource_type, key):        # teardown/实例清理时归还
        self._leases.get(resource_type, {}).pop(key, None)
```

接入约定：
- **步骤处理器接入**（数据实体层）：如 `select_emp: {exclusive: true}` → `acquire("emp_no", 工号, holder)`，失败换下一候选，候选耗尽 → SkipScenario；
- **场景声明接入**（预留给 §六 调度器）：`produces` 里的资源被独占消费时自动登记；
- **归还时机**：默认 session 结束整体释放；配 teardown 的实例在 teardown 成功后即时 `release`（尽早回收供后续场景用）；
- **报告**：租约快照落入 `run.json`（谁持有什么），可视化可画"资源占用甘特图"——排查"为什么这个场景 SKIP 了"时一眼看到候选被谁租走。

### 4.4 为什么第一个接入点选工号池

不是模型偏好，是落地顺序的务实选择：
1. 它是 TDM 当前**唯一已知的真实冲突点**（多个写型场景操作同一人会互相踩踏）；
2. 改动面最小（emp_pool.select 加一个 exclude 参数），能以最低成本**验证 LeaseRegistry 抽象是否好用**；
3. 账号层/配置层冲突要到并行化（§七）才会真实出现，届时注册表已就位，只需新增 resource_type 字符串，零引擎改动。

## 五、待实施 P1：LeaseRegistry + 工号池首个接入

> **✅ 已实施（2026-07-22）**：离线测试 18/18 全绿，包含 8 个新增测试用例。

### 实现点（预计 ~60 行）

1. `engine/scenario_runner.py`：新增 `LeaseRegistry`（§4.3 代码），`RunContext.__init__` 挂 `self.leases = LeaseRegistry()`；
2. `systems/tdm/emp_pool.py`：`EmpPool.select(role, exclude=None)`——候选遍历跳过 exclude 集合；全部被租 → `SkipScenario("候选被租罄，请扩充 emp-pool.yaml")`；
3. `systems/tdm/steps.py` `make_select_emp`：
   ```python
   exclusive = bool(body.get("exclusive"))
   exclude = rctx.leases.leased_keys("emp_no") if exclusive else None
   emp = pool.select(role, exclude=exclude)
   if exclusive:
       rctx.leases.acquire("emp_no", emp["no"], holder=f"{record.scenario_id}#{record.instance_no}")
       record.given["emp_pool"] += "（独占租约）"
   ```
4. shared 的 select_emp 不受租约限制（只读与写型不冲突时无需隔离；冲突时由场景作者显式声明 exclusive）。

### 验收标准

- 离线测试（stub db，追加到 `test_engine_modes.py`）：两个 `exclusive: true` 同角色得到不同工号；候选耗尽 → SKIP 而非 FAIL；teardown 后 release 可再租；
- LeaseRegistry 单测覆盖 acquire 冲突/release/leased_keys；
- emp-pool.yaml 被写型场景使用的角色至少配 3 个候选工号。

## 六、待实施 P2：produces/consumes 资源调度器

**触发条件**：写型场景 ≥ 10 个、或出现"同一资源多状态"需求（既要 IN_PROGRESS 又要 COMPLETED 的会话）时启动。当前 `mode: exclusive` 已够用。

### 6.1 完整契约（在 V2 语法上扩展）

```yaml
# 上游声明产出（V2 已支持 produces，调度器开始消费它）
produces:
  - {resource: inv_session, state: IN_PROGRESS}

# 下游声明消费（新增 consumes 字段）
depends_on:
  - id: IS-PREP-001
    mode: exclusive
    consumes:
      resource: inv_session
      from_state: IN_PROGRESS      # 我需要的输入状态
      to_state: COMPLETED          # 我消费后资源变成的状态（供调度器做状态接力）
```

### 6.2 状态接力复用链（核心增益）

调度器据 `to_state` 判断：场景 A 把会话推到 COMPLETED 后，需要 COMPLETED 会话的场景 C 可**直接复用 A 消费过的实例**（省掉重跑上游+重跑 A）。要点：
- `_Instance` 增加 `current_state`，消费者 PASS 后按其 `to_state` 更新；
- `_acquire_instance` 匹配顺序：`current_state == from_state` 的空闲实例 → 可经状态链推进到位的实例 → 新建；
- 状态机合法性来自场景声明，引擎不内置业务状态机（保持系统无关）；
- 环境配置层资源（§4.2 第四层）在此阶段接入借用-归还：`consumes` 无 `to_state` 或声明 `restore: true` 时强制要求 teardown 恢复。

### 6.3 静态需求计数（可选优化）

加载期遍历 DAG 统计每个上游的独占需求数 N：报告预告"本轮将产生 N 份 IS-PREP-001 数据"；为并行化提供预生产依据。注意须基于**实际收集的用例集**计数（pytest 收集钩子里做，`-k` 过滤后集合会缩小）。

### 7.2 按 DAG 分层并行（P3）

## 九、AI Agent 协作开发指南（拿到本文档后怎么和你的 Agent 对话）

> 本项目的既定实践是 AI 编码 Agent 完成实现、人负责决策与验收。
> 本节给出每个待实施任务的**可直接粘贴的对话剧本**，以及必须遵守的对话纪律。

### 9.1 对话纪律（每个任务开始前先读这个）

1. **先装上下文，再谈需求**。任何任务的第一条消息都让 Agent 读四样东西（见 9.2 开场模板），不要凭记忆口述设计——口述会丢失约束，Agent 会自作主张重新设计。
2. **让 Agent 复述后再动手**。要求它先总结"我理解的目标 / 我会改哪些文件 / 我不会碰什么"，你确认后才允许写代码。这一步能拦住 80% 的方向性跑偏。
3. **守住 §三的4 条设计决策记录**。Agent 如果提出"我觉得预建实例池更好 / 独占可以复用共享实例"，直接引用 §三 驳回——除非它给出新证据。
4. **TDD 顺序不可倒**：先在 `test_engine_modes.py` 加失败的离线测试，再改引擎让它变绿。离线测试是本引擎唯一不依赖 SIT 网络的安全网。
5. **一次对话只做一个任务**（§八表格的一行）。合并任务会让回归定位失效。
6. **验收三件套缺一不可**：离线自测全绿 + 15 个 SIT 场景回归（至少抽 PP-RC-004/PP-RC-007/PP-SEC-001）+ 文档同步（README §六之二 与本文档章节状态）。
