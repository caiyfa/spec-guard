> 创建时间：2026-07-28
> v3 修正：2026-07-29（按用户真实业务闭环重排）
> 输入：[SpecGuard优化升级开发Spec.md](../SpecGuard优化升级开发Spec.md) + 开源项目架构对比 + **用户真实业务闭环**
> 组织方式：**以业务闭环为主线**，优先跑通「发现漏洞 → 反馈研发 → 修正 → 编排 → 定时运行 → 通知」全流程，标准化能力靠后。

## 一、v3 修正说明（与 v2 的差异）

v2 按「标准化能力」排序（异步化、Provider 抽象等 P1），但用户的**真实目标是业务闭环**：

```
① Agent 创建单元测试（读 spec + API 文档）
     ↓
② 发现 spec/接口漏洞（4 类）→ ③ 反馈研发（钉钉/飞书群）
     ↓
④ 研发修正 → 重新拉取文档 → ⑤ 场景编排（DAG）
     ↓
⑥ 定时运行（工作台 UI 配置）→ ⑦ 失败通知群聊 → 可能回到 ② 循环
```

**v3 核心变化**：

1. **新增 3 条 P0 任务链**（H/I/J）直接支撑闭环：闭环编排与模式自动路由、定时任务调度、通知配置
2. **模式系统升级**：5 模式（generate/debug/analyze/chat/**audit**）+ **自动路由**（不需手动选）+ **待办体现** + **Agent 自主切换**
3. **标准化能力整体降档**：异步化/Provider 抽象/权限引擎等从 P1 降到 P2/P3——闭环跑通前不是瓶颈
4. **执行方式决策**：定时运行走**引擎直跑**（不经 pytest，需 DAG 编排 + 中断通知）

**用户确认的闭环要素**：
- 反馈渠道：**钉钉/飞书群聊**（webhook）
- 漏洞 4 类：spec 逻辑缺陷 / spec 与接口不一致 / 生成时发现缺信息 / 运行后发现行为偏差
- 定时调度：**工作台 UI 配置**
- 模式：**自动触发 + 待办体现 + Agent 自主切换**

## 三、闭环与任务链的映射

```
① Agent 创建单元测试 ──────────────┐
                                    │  链 H（generate 模式 + 模式路由）
② 发现 spec/接口漏洞 ──────────────┤
                                    │  链 H-1（audit 模式 + 4 类漏洞）
③ 反馈研发（群聊）─────────────────┤
                                    │  链 J（钉钉/飞书 webhook）
④ 修正 → 重新拉取文档 ─────────────┤
                                    │  链 H-5（pull 信号 → 自动 audit）
⑤ 场景编排（DAG）──────────────────┤
                                    │  链 H（DAG 已有）+ 链 F-1（plan 落盘）
⑥ 定时运行 ────────────────────────┤
                                    │  链 I（APScheduler + 引擎直跑）
⑦ 失败通知群聊 → debug ────────────┘
                                    链 J（通知）+ 链 H（debug 路由）
                                    ↺ 回到 ② 循环
```

**模式自动切换贯穿全程**（链 H-2/H-3/H-4）：
- 发消息 → 按上下文/意图自动选模式（无需手动）
- Agent 工作流阶段转换 → 自主 switch_mode
- 模式切换 → 待办面板 + 切换卡片 + 模式徽章三处体现

## 四、执行路线图（v3：先跑通闭环 MVP）

> 用户已确认：APScheduler 依赖 ✅、定时运行走引擎直跑 ✅。
> **并行策略核心**：所有跨链依赖都是「接口依赖」而非「实现依赖」，用降级实现解耦，5 条 P0 链第 1 天全并行。

### 第 0 天：接口冻结会（2 小时，并行开发前提）

冻结 4 个跨链接口签名，各链只依赖签名：

```python
# 接口 1：路径（F-1 提供，H/I 消费）——降级：先返回 SG_ROOT 旧路径
def specguard_dir(workspace_root=None, custom_path="") -> Path
def reports_dir() -> Path
def drafts_dir() -> Path

# 接口 2：通知（J 提供，H/I 消费）——降级：写 notify_log 表后 return True
async def send_notification(config: dict, event: str, payload: dict) -> bool

# 接口 3：加密（A-3 提供，J 消费）——降级：透传原样返回
def encrypt(plaintext: str) -> str
def decrypt(ciphertext: str) -> str

# 接口 4：WS 事件（H 提供，前端消费）——前端先用 mock 事件流开发
{"type": "mode_switch", "from": str, "to": str, "source": str, "reason": str, "auto": bool}
{"type": "todo_update", "todos": [{id, title, status, mode}]}
```

### 依赖矩阵（全部可降级，无阻塞性依赖）

| 依赖方 → 被依赖方 | 内容 | 降级方案 |
|------------------|------|---------|
| J → A-3 | crypto 加密 | 透传实现，A-3 完成后替换 |
| H-1 / I → F-1 | 落盘路径 | 先用 SG_ROOT 旧路径，F-1 完成后切换 |
| H-1 / I → J | send_notification | 空实现记 notify_log，J 完成后接通 |
| H 前端 → H 后端 | WS 事件结构 | 第 0 天冻结 schema，前端 mock 开发 |

### 分批方案

**方案 A：3 人（2 周 MVP）⭐推荐**

| 人员 | 第 1 周 | 第 2 周 |
|------|--------|--------|
| 人 1（后端） | 链 A（A-3→A-2→A-1）→ 链 J | J 收尾 → 端到端联调 |
| 人 2（后端） | 链 F-1 → 链 H-1 | H-5 → H-2 → 联调 |
| 人 3（后端+前端） | 链 I | H-3/H-4 后端 → 前端页面收尾 |

前端贯穿两周：第 1 周 mock 开发（待办面板/模式徽章/切换卡片/通知配置页），第 2 周 Schedules 页 + 联调。

**方案 B：2 人（2.5-3 周）**：人 1 走 A→J→I→联调；人 2 走 F-1→H 全链→全部前端。

**方案 C：1 人（约 4 周）**：A-3 → J → A-2/A-1 → F-1 → I → H（H-1→H-4→H-3→H-2→H-5）→ 联调。

**MVP 验收（闭环走通）**：

## 八、风险与缓解（v3）

| 风险 | 影响 | 缓解 |
|------|------|------|
| 模式自动路由误判（用户想做 A 却路由到 B） | 链 H | 手动锁定兜底 + 路由原因可见 + 置信度低的意图默认 chat |
| Agent 自主切换模式失控（来回切） | 链 H | 切换需 reason + 待办体现可审计 + 单次会话切换次数软上限 |
| 通知风暴刷屏 | 链 J | 批量合并 + 限流 + 按事件订阅 |
| APScheduler 新依赖 | 链 I | 评审；workers=1 单进程无竞争 |
| 引擎直跑与 pytest 产物不一致 | 链 I | 复用 report_writer 对齐格式 |
| 闭环串联点多（H/I/J/F-1 交互），联调复杂 | 全部 | 每链独立验收 + 端到端闭环门禁（总览第四节） |
