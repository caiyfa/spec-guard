# 任务链 F-1：文档归属架构

> 优先级：**P0（上调，修正版）**
> 并行性：✅ 独立（需业务决策），可与任务链 A/G 并行启动
> 预计工期：架构决策评审 1-2 天 + 落地 2-3 天
> 文档依赖：[总览](./00-总览与任务链编排.md)
> 修正说明：**F-1 从 P2 上调到 P0**。初版低估了它的阻塞性——场景创建流水线（G2-1）是核心功能，但草稿如何入库、报告如何归档没有闭环（依赖本链的 `.specguard/` 约定）。不做 F-1，G2-1 的产物会散落到各处，未来重构成本高。

---

## 一、目标

明确 SpecGuard 各类文件归属，引入 `.specguard/` 工作区根目录约定，为场景创建流水线（G2-1）提供完整闭环。

**用户决策**：文档应该归属到对应的 spec 仓库或工作空间，在根目录开辟独立空间存储 specguard 相关文档。

---

## 二、现状问题

SpecGuard 产生的各类文件归属混乱（[验收期优化点总表 2.1](../SpecGuard验收期优化点总表.md#21-specguard-产生的各类文件存在哪里)）：

| 文件类型 | 当前位置 | 问题 |
|----------|----------|------|
| 场景 YAML | `scenarios/`（spec 仓库内） | 需手动/Git 提交 |
| 测试计划 | `plans/`（spec 仓库内） | 禁止手动新建，delta 生成 |
| 运行报告 | `reports/{timestamp}/`（spec 仓库内，.gitignore） | 服务器本地，不版本化 |
| Agent 草稿 | `drafts/`（spec 仓库内，.gitignore） | 评审后才移入 scenarios/ |
| 工作区注册表 | `specstd/workspaces/registry.yaml`（SpecGuard 本地） | 服务器运行时状态 |
| 用户/DB | `workbench/backend/data/workbench.db`（SpecGuard 本地） | SQLite，不提交 |
| Git 克隆 | `specstd/workspaces/_clones/`（SpecGuard 本地） | 可能撑爆系统盘 |

**阻塞性**：G2-1 场景创建流水线的产物（草稿、info_pack、报告）当前散落到各处，无法闭环。

## 三、设计方案：`.specguard/` 工作区根目录约定

### 目录结构

```
{工作区根目录}/                      # 即 spec 仓库根
├── spec.md                          # 原始 spec（用户维护）
├── scenarios/                       # 场景库（已入库，版本化）—— 保留原位置
├── .specguard/                      # 新增：SpecGuard 专属目录
│   ├── README.md                    # 说明本目录用途（自动生成）
│   ├── drafts/                      # Agent 草稿（评审前）
│   ├── plans/                       # 测试计划（delta 生成）
│   ├── reports/                     # 运行报告（按时间戳）
│   ├── info_packs/                  # 基础信息包（场景 ↔ 文件关联）
│   └── .gitignore                   # 本目录的 git 忽略规则
│       # 忽略 reports/（运行产物）
│       # 忽略 drafts/（未评审草稿）
│       # 保留 plans/（版本化资产）
│       # 保留 info_packs/（版本化资产）
```

**SpecGuard 仓库自身**（`D:\work\tdm-code\specguard`）只保留引擎代码、智能层、工作台，不再存工作区产物。

### 归属规则

| 文件类型 | 新归属 | 版本化策略 |
|----------|--------|-----------|
| 场景 YAML | `{workspace}/scenarios/` | ✅ 提交（已入库资产） |
| 测试计划 | `{workspace}/.specguard/plans/` | ✅ 提交（与 spec 同步演进） |
| 运行报告 | `{workspace}/.specguard/reports/` | ❌ gitignore（运行产物） |
| Agent 草稿 | `{workspace}/.specguard/drafts/` | ❌ gitignore（评审前） |
| 基础信息包 | `{workspace}/.specguard/info_packs/` | ✅ 提交（场景 ↔ 文件关联） |
| 工作区注册表 | `{specguard}/specstd/workspaces/registry.yaml` | SpecGuard 本地 |
| 用户/DB | `{specguard}/workbench/backend/data/` | SpecGuard 本地 |
| Git 克隆 | `{specguard}/specstd/workspaces/_clones/` 或自定义 | SpecGuard 本地 |

### 【修正补充】`.specguard/` 位置可配置

**初版隐患**：`.specguard/` 自动创建在 spec 仓库根目录，可能侵入用户的仓库结构。

**修正**：`.specguard/` 位置可配置：
- 默认 `{workspace}/.specguard/`
- 用户可在工作区注册时指定其他位置（如外挂存储 `/data/specguard-artifacts/{workspace}/`）
- 参考任务链 1.1 的 Git 克隆自定义目录，同样逻辑适用

```python
# specstd/workspace.py

def specguard_dir(workspace_root: Path = None, custom_path: str = "") -> Path:
    """获取工作区的 .specguard 目录（可配置位置）。

    custom_path 非空时用自定义位置，否则默认 {workspace}/.specguard/
    """
    ws = workspace_root or get_active_workspace_root()
    if not ws:
        raise RuntimeError("无激活工作区")

    if custom_path:
        sg_dir = Path(custom_path)
        # 路径穿越防护
        sg_dir = sg_dir.resolve()
        if not _is_safe_custom_path(sg_dir):
            raise ValueError(f"非法自定义路径: {custom_path}")
    else:
        sg_dir = ws / ".specguard"

    sg_dir.mkdir(parents=True, exist_ok=True)
    _ensure_specguard_meta(sg_dir)
    return sg_dir
```

## 四、落地改动

### 1. specstd/workspace.py：新增 `.specguard/` 路径解析

```python
def drafts_dir() -> Path:
    return specguard_dir() / "drafts"

def plans_dir() -> Path:
    return specguard_dir() / "plans"

def reports_dir() -> Path:
    return specguard_dir() / "reports"

def info_packs_dir() -> Path:
    return specguard_dir() / "info_packs"

def _ensure_specguard_meta(sg_dir: Path):
    """首次创建时生成 README + .gitignore（幂等）。"""
    gitignore = sg_dir / ".gitignore"
    if not gitignore.is_file():
        gitignore.write_text(
            "# SpecGuard 运行产物（不提交）\n"
            "reports/\n"
            "drafts/\n\n"
            "# 以下为版本化资产（提交）\n"
            "# plans/\n"
            "# info_packs/\n",
            encoding="utf-8",
        )
    readme = sg_dir / "README.md"
    if not readme.is_file():
        readme.write_text(
            "# .specguard/\n\n"
            "本目录由 SpecGuard 自动管理。\n\n"
            "- `drafts/`：Agent 生成的场景草稿（评审后移入 `../scenarios/`，未评审不入 git）\n"
            "- `plans/`：delta 导入生成的测试计划（版本化）\n"
            "- `reports/`：运行报告（运行产物，不入 git）\n"
            "- `info_packs/`：场景的基础信息包关联（版本化）\n",
            encoding="utf-8",
        )
```

### 2. 工具层路径迁移

| 工具/服务 | 原路径 | 新路径 |
|-----------|--------|--------|
| `draft_writer` | `SG_ROOT/drafts/` | `drafts_dir()` |
| `services/plan_store` | `SG_ROOT/plans/` | `plans_dir()` |
| `services/runner` 报告输出 | `SG_ROOT/reports/` | `reports_dir()` |
| `services/scenario_meta` info_pack | DB | `info_packs_dir()/{scenario_id}.yaml` |

### 3. 文档同步

- `AGENTS.md` Repository Structure：移除 `drafts/`、`plans/`、`reports/` 顶层描述，改为「各工作区的 `.specguard/` 目录」
- `.gitignore`：移除顶层 `drafts/`、`reports/`、`plans/`

### 4. 工作区注册扩展

前端工作区注册表单新增「.specguard 目录位置」字段（可选，默认 `{workspace}/.specguard/`）。

## 七、架构决策评审（需业务方参与）

**本链含架构决策，需业务方确认以下问题**：

1. `.specguard/` 默认放在 spec 仓库根目录是否可接受？（可能侵入用户仓库结构）
2. `.specguard/` 位置可配置的粒度（全局统一 vs 每工作区独立）？
3. `scenarios/` 保留在根目录（与 spec 同级），而 drafts/plans 在 `.specguard/`——这种"已入库 vs 未评审"的分层是否符合直觉？
4. 存量数据（现有 drafts/plans/reports）是否需要迁移，还是直接废弃（反正 .gitignore 了）？

**建议**：架构决策在第 1 波启动时即开始评审，与开发并行，避免阻塞。
