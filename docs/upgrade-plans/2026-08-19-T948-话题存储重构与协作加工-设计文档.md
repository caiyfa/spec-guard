## 1. 总体架构决策

### D1 存储分双层：JSONL 事实源 + md 派生视图
原文消息以 **JSONL 为唯一事实源**（每行一条消息的原始结构化数据，保 message_id），
md 是从 JSONL 渲染的**派生视图**（LLM prompt 素材 + 人可读），可随时重建、允许删除。
与项目既有铁律「图谱从文件派生而非重跑 LLM」同构：原文是事实，展示层是投影。

### D2 共享模型：方案 A 全通道（已拍板，含 docs/minutes 权限可见性）
- **chats 快照与话题卡片**：迁工作区共享区（`{ws}/.specflow/feishui_pool/`，即 `specflow_dir("")`），
  三角色复用同一份原文与同一套话题，不再按 emp 重复拉取/存储。
- **docs/minutes（拍板扩展）**：也迁共享区，但带**飞书权限元数据可见性过滤**——
  拉取时同步拉取飞书侧权限信息（§2.6），共享区材料对用户 X 可见 ⟺ 飞书侧 X 本来就能看。
  依据：这些内容在飞书里本身就是多人共享的（文档可授权给群、可单独授权给人）。
- 权限语义改写：AGENTS.md「watch 配置即显式授权载体」升级为**工作区级授权**——
  拉取范围仍由个人 watch 配置决定（谁配置谁拉），但落盘后的**可见范围跟随飞书权限**，
  不再扩大也不缩小（chats 快照的可见范围=工作区内用户，因拉取者必在群内且办公场景等同同事间转述，需在 AGENTS.md 明示）。
- 重复拉取无害化：JSONL 按 message_id 幂等合并（§3.3），多个用户同时点同步只是
  重复 API 调用，不产生重复数据——**无需拉取锁/owner 选举**，最多加进程内节流。

### D3 候选/已确认合并为状态字段
话题卡片增加 `status: draft | confirmed | rejected`，「确认」从跨区提升（私有
`_candidate_topics.yaml` → 共享 `topics.yaml`）退化为**同一存储内的状态翻转**。
`_candidate_topics.yaml` 与私有 `facts` 双轨在 T-949 合并为共享区单文件。

### D4 编辑并发：乐观锁 + append-only 历史
卡片带 `rev` 整数版本号；编辑请求携带 `base_rev`，不匹配返回 409 + 最新卡片
（前端提示「已被 XX 编辑过」并刷新）。每次变更追加一条历史记录（不可篡改留痕）。
不做事务锁/字段级合并——办公协作量级下乐观锁 + 留痕已足够，YAGNI。

### D5 分三任务块交付（每块独立可验收）
| 任务块 | 范围 | 存储位置 |
|---|---|---|
| **T-948** 存储与话题模型 | JSONL 双层、契约修复、按天拉取、幂等合并、图片 imgmap、话题 schema v2（keywords/status/author/agent_origin/rev）、编辑 API + 历史、聚类输出 message_ids | 仍在**私有区**（不动位置，风险隔离） |
| **T-949** 共享化迁移 | chats 快照迁共享区、watch 工作区级合并、话题单文件化（状态制）、历史迁共享、docs/minutes 迁共享 + 权限元数据拉取与可见性过滤（§2.6）、AGENTS.md 授权语义更新 | 迁**共享区** |
| **T-950** 前端工作台 | 双栏工作台、色卡泳道、状态徽标、编辑弹层（含 AI 原稿对照 diff）、历史抽屉、候选双列表移除、材料可见性按权限过滤呈现 | — |

## 2. 数据模型设计

### 2.1 消息 JSONL（统一两通道的 schema）

文件：`chats/{chat_sha8}/{yyyymmdd}.jsonl`（与 md 同目录共存），每行：

```json
{
  "message_id": "om_x100b670b24462ca8b146ee0cad5da05",
  "position": "3021",
  "sender_id": "ou_62fe8d6439bc89e441af35bcf75ea98b",
  "sender_name": "蔡云飞",
  "ts": "2026-08-18T14:07:00",
  "msg_type": "text",
  "content": "@贺文君 正好目前数据权限很散乱 这一波升级一下",
  "image_key": "",
  "reply_to": "om_x100b670b2935f0b8dda2dff0eb731ee",
  "mentions": [{"id": "ou_5655...", "key": "@_user_1", "name": "贺文君"}],
  "origin": "pull"
}
```

字段规则：
- `message_id`：幂等去重键。拉取通道取 CLI `message_id`；事件直写通道无消息 ID，
  用 `"evt:{event_id}"`（前缀区分，天然不与拉取键冲突）。
- `position`：飞书会话内单调序号（CLI 实测字段），**排序权威键**（同秒消息稳定排序）。
  事件通道无此字段，填 `""`，排序回退 `(ts, sender_id, content哈希)`。
- `ts`：ISO 本地时间。拉取通道从 CLI `"2026-08-18 14:07"` 字符串直接解析
  （**禁止** `int(create_time)`——现 `_render_chat_lines` 的做法对字符串会抛 ValueError）；
  事件通道从毫秒时间戳换算。
- `origin`：`pull`（校对/手动同步拉取）| `event`（实时直写）。
- 撤回/编辑：CLI `deleted/updated` 字段拉取时如实落 `msg_type`/`content`
  （deleted=true 的行保留但 content 置 `"[已撤回]"`，诚实呈现）。

**md 派生规则**（`render_md_from_jsonl`，替代现 `_render_chat_lines` 消费 items）：
按 position 排序后渲染 `[HH:MM] 发送人: 内容`（文本）；图片行 `[HH:MM] 发送人: [图片#N]`
（N 为 imgmap 键序号）；其余类型 `[HH:MM] 发送人: [{msg_type}消息]`。行格式与现有
`_PROMPT` 约定完全一致——**聚类 prompt 零改动兼容**。

### 2.2 图片消息闭环（复用 docs 通道既有链路）

- 拉取时对 `msg_type == "image"` 消息提取 `image_key` 落 JSONL；
  生成 `chats/{sha8}/{day}.imgmap.json`（与 docs 同构）：
  `{"图片#1": {"media_key": "...", "caption": "", "caption_by": "none", "status": "pending"}}`。
- 现有设施直接复用，零新概念：`captions._iter_pending` 已扫 chats 目录（通道存在、
  只是现在无生产者）；`transcribe_images` 转述、`material-image` 字节代理、
  caption 人工补写全部沿用。
- ⚠ ~~实施时先实测确认~~ **已实测（2026-08-19）**：image 消息的 `image_key` 在
  `content` 字符串内，格式 `"[Image: img_v3_xxx]"`（顶层无 image_key 字段）；
  解析用正则 `\[Image:\s*(.+?)\]` 提取。
- `--download-resources` 暂不启用（转述走 media_key 按需下载即可，避免全量拉资源）。

### 2.3 话题卡片 schema v2

```yaml
id: tp:3f9a2c-20260819-01        # 不变：{sha8}-{day}-{seq}，id 稳定性铁律延续
title: 导出权限过滤
summary: 按 corpCode+groupLevel 过滤，缺失平台行剔除
keywords: [导出, 数据权限, corpCode]     # 新增 R7：LLM 生成 + 用户可编辑
chat_sha8: 3f9a2c
window: ['2026-08-19T14:00', '2026-08-19T14:07']   # 保留（人读 + 兜底）
message_ids:                            # 新增 P2：精确消息锚定
  - om_x100b670b24462ca8b146ee0cad5da05
  - om_x100b670b2935f0b8dda2dff0eb731ee
message_count: 5
participants_count: 3
source: chats/3f9a2c/20260819.md        # 不变（md 视图路径）
continues: tp:3f9a2c-20260812-01        # 演进链保留（防幻觉校验沿用）
status: draft                           # 新增 D3：draft | confirmed | rejected
author: {emp: '90024166', name: 蔡云飞}  # 新增：创建人（自动生成时=触发同步者）
rev: 3                                  # 新增 D4：乐观锁版本号，每次成功编辑 +1
agent_origin:                           # 新增 R8：agent 最近一次生成的原始版本
  title: 导出权限
  summary: 权限过滤讨论
  keywords: [权限]
  model: qwen-max
  generated_at: '2026-08-19T09:00:00'
  prompt_version: pv2
last_edited_by: {emp: '90000001', name: 王测试}
last_edited_at: '2026-08-19T10:30:00'
```

存储（T-948 私有区，T-949 迁共享区）：`_topics.yaml` 取代 `_candidate_topics.yaml`
（单文件承载全部状态，rejected 也留卡片不删除——状态制下「拒绝」是标记不是清除）。
`facts._TOPIC_KEY_FIELDS` 白名单同步扩展（T-949），图谱 builder 派生时过滤
`status != confirmed`（与现在「rejected 不进图谱」语义对齐）。

`message_ids` 与 `window` 并存策略：聚类 prompt 同时输出两者（§4）；高亮/计数优先
message_ids（精确），缺失时回退 window 字符串区间（存量兼容 + LLM 偶发漏输出兜底）。

### 2.4 编辑历史（append-only 留痕）

文件：`_topic_history.jsonl`（T-948 私有区 / T-949 迁共享区），每次成功变更追加一行：

```json
{
  "at": "2026-08-19T10:30:00",
  "topic_id": "tp:3f9a2c-20260819-01",
  "editor": {"emp": "90000001", "name": "王测试"},
  "action": "edit",
  "base_rev": 2,
  "changes": {
    "title": {"from": "导出权限", "to": "导出权限过滤"},
    "keywords": {"from": ["权限"], "to": ["导出", "数据权限", "corpCode"]}
  }
}
```

- `action` 枚举：`create`（聚类产出）/ `draft`（重新分段）/ `commit`（勾选提交）/
  `edit`（人工编辑）/ `regen`（单卡重生成）/ `confirm` / `reject`。
- `regen` 的 changes 记录 `agent_origin` 新旧快照（旧 origin 版本由此可追溯，不丢）。
- 读路径 `GET /topics/{id}/history` 直接倒序过滤该 topic_id。
- 不进卡片正文（卡片只留 `last_edited_*` 摘要），读卡片零开销。
- 事件直写/聚类等**系统自动**动作 editor 记 `{emp: "", name: "system"}`。

### 2.5 agent_origin 对比语义（R8 的落地面）

- 生成（create/draft/regen）时写 `agent_origin`；**人工编辑永不触碰它**。
- 对比口径：`当前字段 vs agent_origin` = 用户修正量。后续优化生成逻辑时，
  按 (model, prompt_version) 分组统计修正模式（标题收紧率、关键词增补率等）——
  数据从现在开始积累，分析功能本期不做（YAGNI，仅保证数据在）。
- `prompt_version`：`topic_cluster.py` 三个 prompt 常量旁各配版本号
  （`_PROMPT_VERSION = "pv2"`，本次改 prompt 时从 pv1 升 pv2），生成时落 origin。
  A/B 新 prompt 时递增，即可按版本归因对比。

### 2.6 材料权限元数据与可见性（T-949，docs/minutes 共享的权限地基）

**能力实测（2026-08-19）**：lark-cli 已封装权限查询，且支持 minutes token：
- `drive +member-list --token {token}`：协作者列表（用户 open_id / 群 chat_id + perm 角色）
- `drive +permission-get-setting --token {token}`：公开性设置（组织内可见/关闭等）

**拉取时落权限元数据**（扩展现有 meta sidecar 机制，`fd-*.meta.json` / `fm-*.meta.json` 新增键）：
```yaml
perm:
  pulled_at: '2026-08-19T09:00:00'
  public: false                  # permission-get-setting：组织内/互联网公开
  member_users: [ou_a, ou_b]     # 被授权用户 open_id（含 owner）
  member_chats: [oc_x]           # 被授权群 chat_id
```

**可见性判定**（共享区材料清单 API 按请求用户过滤）：
```
visible(X, material) = material.perm.public
                    ∨ X.open_id ∈ member_users
                    ∨ (X 的群列表 ∩ member_chats) ≠ ∅
```
- X 的群列表复用现有 `list_my_chats`（`im +chat-list --as user`，按请求用户 token）；
  结果进程内缓存（TTL 5min），避免每次清单全量拉群。
- perm 缺失（存量材料/拉取权限接口失败）：**默认不可见**（保守）+ 材料详情提示
  「权限信息缺失，重新同步可补拉」——诚实呈现，不静默降级为全可见。
- 拉取顺序：先 member-list + get-setting，后正文（权限元数据与正文同次同步落盘；
  权限接口失败不阻断正文落盘，perm 记 `pulled_at: null` 走缺失分支）。
- 妙记权限模型与文档不同（owner/组织内/链接分享），member-list 对 minutes token
  实测可调，字段兼容性在 T-949 首步用真实 token 验证并记经验包。

## 3. 同步链路改造（T-948 主体）

### 3.1 契约修复（P1，最优先）

`sync_chat` 消费 `data.messages`（兼容旧 `data.items` 一行，观察期后删），
字段映射按 §2.1；单群拉取 0 条消息 → **不写文件、返回体计数单列**
`{"chats": 4, "chats_empty": 1, "errors": []}`，前端 notice 如实显示
「群聊 4（其中 1 群当日无消息）」——消灭「0 字节假成功」诚实性缺口。

### 3.2 按天拉取 + 历史补拉（P3）

```python
sync_chat(specflow_emp_base, chat_id, day)   # day 参数语义激活
# CLI 参数：
#   --start {day}T00:00:00+08:00  --end {day+1}T00:00:00+08:00
#   --order asc --page-all --page-limit 40   # 单日上限 40 页×50 条 = 2000 条，防御性上限
```

- `sync_all` 对每个群循环拉 **最近 `chat_days` 天**（默认 7，配置项终于生效）：
  `for d in [today-6 .. today]: sync_chat(base, chat_id, d)`。
  「立即同步」由此获得历史补拉能力——回答用户原始问题「只按一下按钮能不能覆盖介入所需的任意日期」：能，窗口内全部重建。
- watcher 每日校对 job：只重拉**当天**（行为不变，语义从「最近 50 条写今天」变为「当天全量重建」）。
- 事件直写（`_direct_write_chat`）：改写 JSONL（`evt:{event_id}` 键追加）后**重建当天
  md**；下一次校对重拉时，拉取结果按 message_id 天然吸收/淘汰 evt 条目
  （同消息拉取版覆盖事件版；当天全量重建以拉取为权威）。
- 单群单日 API 成本：1 群 1 天 ≈ 1~2 页请求；7 天窗口 4 群 ≈ 30 次请求，可接受。

### 3.3 JSONL 幂等合并（D2 的技术前提）

```python
def merge_chat_jsonl(day_file: Path, incoming: list[dict]) -> dict:
    """按 message_id 合并：新条目追加、同 id 覆盖（updated/deleted 状态刷新）。
    返回 {"added": n1, "updated": n2}。合并后按 (position, ts, sender_id) 排序重写，
    最后同步重建 md 与 imgmap。"""
```

- 文件级并发：T-948 私有区内单用户无并发；T-949 共享化后多用户同时同步 →
  共享文件写加 `threading.Lock`（后端进程内）+ 临时文件原子替换
  （`write tmp → os.replace`，进程内锁足够：uvicorn workers=1 是部署铁律）。

### 3.4 存量数据迁移

- 现网 8 个 0 字节 md：直接删除（无信息量），首次同步按 7 天窗口重建。
- 非空 md（如有）：一次性迁移脚本读 md 反推 JSONL 不可靠（无 message_id）——
  **不迁移**，md 保留只读、JSONL 从下次拉取新生成；聚类只消费有 JSONL 的日期。
  当前全部为空文件，实际无迁移负担（迁移脚本按此简化，不留通用逻辑）。

## 4. 聚类与介入流程改造（T-948）

`_PROMPT` / `_DRAFT_PROMPT` / `_REGEN_PROMPT` 升级（prompt_version → pv2），新增输出要求：

```
2. 每个话题给出：title（≤20字）、summary（≤80字结论摘要）、keywords（2~5个）、
   msg_lines（该话题覆盖的消息**行号列表**，行号=消息在原文中的 1-based 序号）、
   participants_count（参与人数）
```

- 行号 → message_id 映射：聚类前把当天 JSONL 渲染行序列与 message_id 列表对齐
  （渲染函数返回 `(md_text, line_message_ids)`），LLM 输出 msg_lines 后精确换算。
  行号列表同时天然消除「同 HH:MM 内并行话题归属歧义」。
- `_count_messages` 改为 `len(message_ids)`（window 回退逻辑保留）。
- `draft_chat_segments` / `commit_drafts` / `regen_candidate` 全链路：
  产出卡片带 `status="draft"`、`author`、`agent_origin`、`rev=1`，
  并追加 history（action=draft/commit/regen，editor 触发用户）。
- `commit_drafts` 的「覆盖该群该天旧候选」语义调整为：旧卡片 `status → rejected`
  （不再物理删除——留痕），勾选段作为新 draft 写入。

## 6. 前端工作台（T-950 概要，批准 T-948 后出详细设计）

- **单页双栏**：左栏消息时间轴（JSONL 渲染，含图片占位/转述描述）、右栏话题卡片流；
  顶部仅「群 / 日期 / 重新 AI 分类」三个控件。监听状态卡、材料页签在介入模式下折叠。
- **色卡泳道**（用户 R 需求，git-log 类比）：话题卡按 window 时间位置水平铺排，
  window 重叠的话题分泳道（lane），每话题一色卡；hover/点击色卡 → 左栏对应消息
  **精确高亮**（message_ids 集合匹配）+ 自动滚动到首条；`continues` 链泳道连线。
- **卡片交互**：状态徽标（draft/confirmed/rejected 筛选器）；内联「编辑」
  （title/summary/keywords 表单 + **AI 原稿对照**：编辑时左侧展示 agent_origin，
  差异字段高亮——R8 的查看入口）；「重生成」；「历史」抽屉（timeline 列表）。
- **移除**候选/已确认双列表：单一卡片流 + 状态筛选。
- 409 冲突处理：弹层提示「已被 {last_edited_by.name} 编辑」，展示最新卡片差异后重试。
