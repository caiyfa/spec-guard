# SpecGuard 飞书材料池监听选择器设计（用户/群聊）

- 日期：2026-08-17
- 状态：**v1.1 已实施**（2026-08-17 全量交付：后端 7 用例 + 端点 3 个 + 前端选择器弹层；test_specstd 1485 passed / 2 failed 为存量隔离污染（单独复跑通过，与本次无关）；release_check PASS；前端 build 通过）
- 范围：workbench 后端 + 前端 + 测试；不触碰引擎冻结层（engine/）、不触碰 specstd 规范层

## 1. 背景与目标

### 1.1 现状问题

飞书材料池（飞书知识图谱一至三期）的同步范围配置存在三个缺口：

1. **无选择器**：`FeishuReviewPanel.tsx` 同步设置弹层只有两个 textarea——手填群聊 chat_id、手填文档 token，无法从群列表/通讯录中选择。
2. **无用户监听维度**：`feishu_watch.yaml` 仅有 `chats`/`docs`/`minutes_days`/`chat_days`，没有"监听某个飞书用户"的语义。事件订阅 `im.message.receive_v1 --as bot` 不区分会话类型、不按发送人过滤。
3. **直写授权缺口**：`feishu_watcher._direct_write_chat` 收到任何群聊消息都直写落池，不校验 chat_id 是否在 watch 授权列表——"同步范围即授权范围"的约定在实时监听路径上未生效。

### 1.2 目标

- 群聊选择器：从"我的群聊列表"勾选群聊加入 `watch.chats`（替代纯手填）。
- 用户选择器：通讯录搜索用户加入 `watch.users`，并勾选监听范围。
- 用户监听语义（本期）：
  - 群内按发送人过滤（直写阶段，`sender_id ∈ users` 才直写）；
  - 用户产出的妙记（`minutes +search --owner-ids ou_xxx` 轮询）；
  - 用户产出的文档（`docs +search --filter {"owner_ids":[ou_xxx]}`，Search v2，dry-run 已验证可行）。
- 顺手修复：直写授权校验（D5）。

### 1.3 能力核实记录（2026-08-17 实测）

| 能力 | 命令 | 结论 |
|---|---|---|
| 群聊/单聊列表 | `im +chat-list --as user --types p2p,group --sort active_time --page-all` | ✅ 返回 chat_id/name/chat_mode/p2p_target_id |
| 用户搜索 | `contact +search-user --query 姓名 --has-chatted --as user` | ✅ 返回 open_id/name/email/department |
| 妙记按用户 | `minutes +search --owner-ids ou_xxx` | ✅ 支持任意 open_id（非仅 me） |
| 文档按用户 | `docs +search --query <kw 或 ""> --as user` | ⚠️ 空 query 实测可用；但 CLI `--filter owner_ids` 实测**不生效**（对照实验：过滤后仍返回非指定 owner 文档）——必须应用侧按 `result_meta.owner_id` 过滤 |
| 私聊事件 | `im.message.receive_v1 --as bot` | ⚠️ 仅 bot 参与的会话（群聊 + 用户与 bot 单聊），收不到两用户间私聊 |

## 2. 关键决策记录

| D | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 事件过滤位置 | **应用侧过滤**（watch 配置驱动） | 配置变更即时生效，无需重启 consume 子进程；与 T-924 配置驱动启停架构一致；个人 bot 消息量级下全量接收成本可忽略 |
| D2 | 私聊监听 | **本期不做** | bot 身份收不到不涉及自身的两用户私聊（飞书能力边界）；用户确认本期范围收敛 |
| D3 | 用户文档检索 | `docs +search`（Search v2，空 query 实测可用）+ **应用侧按 result_meta.owner_id 过滤** | CLI `--filter owner_ids` 实测不生效（2026-08-17 对照实验）；搜索召回范围为「当前用户可见文档」，应用侧交集过滤后得目标用户文档，召回边界诚实呈现 |
| D4 | 发送人过滤落池语义 | **仅直写过滤**；每日 03:00 校对重拉保持全量覆盖 | 用户确认：实时流里只关注指定人，快照最终对齐飞书侧（诚实呈现） |
| D5 | 直写授权校验 | chat_id ∈ watch.chats 才直写，否则丢弃 | 修复全量落池隐患，兑现"同步范围即授权范围" |
| D6 | 选择器数据源身份 | 当前登录用户身份（`--as user`，后端 `_run_lark` 既有模式） | 选择器展示"我自己的群/通讯录"；监听执行仍按各 emp 的 `.lark-cli/{emp}` 身份 |

## 3. 数据模型（watch 配置 v2）

`feishu_watch.yaml`（`.specflow/{emp}/`）：

```yaml
chats:
  - chat_id: oc_xxx
    name: 需求讨论群        # 新增：选择器勾选时回填；手填的允许留空
docs:
  - token: FBxod
    url: https://...
    owner_open_id: ou_yyy  # 新增：用户文档搜索勾选时回填（标注归属人）；手填的可无
users:                     # 新增：用户监听维度
  - open_id: ou_yyy
    name: 张三
    scopes: [group_sender, minutes, docs]   # 合法枚举：group_sender / minutes / docs
minutes_days: 30
chat_days: 7
```

兼容性：
- `_DEFAULT_WATCH` 增加 `users: []`；`load_watch_config`/`save_watch_config` 白名单合并逻辑不变，旧配置自动补齐 `users: []`，未知字段照旧丢弃。
- 保存时校验：`users[].open_id` 必填；`scopes` 仅保留合法枚举值（非法值丢弃）；按 open_id 去重（后写覆盖）；允许空 `scopes`（保存但无监听动作）。

## 4. 后端设计

### 4.1 新端点（`workbench/backend/routers/feishu_pool.py`，全部只读、`--as user`）

| 端点 | 底层命令 | 返回 |
|---|---|---|
| `GET /feishu-pool/chats` | `im +chat-list --as user --types p2p,group --sort active_time --page-all --format json` | `[{chat_id, name, chat_mode}]`；p2p 项附带 `peer_open_id`，前端标记不可选（本期不做私聊） |
| `GET /feishu-pool/users?query=<kw>` | `contact +search-user --query <kw> --has-chatted --as user --format json` | `[{open_id, name, email, department}]` |
| `GET /feishu-pool/user-docs?open_id=<ou>&query=<kw 可空>` | `docs +search --query <kw 或 ""> --as user --format json` → **应用侧按 `result_meta.owner_id == open_id` 过滤** | `[{token, title, url, doc_type, owner_id, owner_name}]`（token 即 result_meta.token，供 `docs +fetch` 拉取） |

统一纪律：
- 单条失败记 `errors` 返回（诚实呈现，不抛 500）；未认证/权限不足同样落入 `errors`。
- `users` 端点 query 为空时返回空列表（不调用 CLI，避免无关键词扫全量）。
- `user-docs` 端点 query 允许为空（Search v2 空 query 实测可用；空 = 搜当前用户可见文档全集后按 owner 过滤）。

### 4.2 watch PUT 扩展

- `PUT /feishu-pool/watch` 接收含 `users` 的配置，校验逻辑见 §3。
- 保存后复用 T-924 配置驱动启停：经 `get_registry().start_user(emp)` 拉起该用户监听（幂等，失败不阻断保存），响应带 `watcher` 状态。

### 4.3 同步与轮询扩展（`feishu_sync_service.py` / `feishu_watcher.py`）

- `sync_minutes(specflow_emp_base, days, owner_ids=None)`：`owner_ids` 为 None 时保持现状（`--owner-ids me`）；指定时传 `--owner-ids <ou_a,ou_b>`（接口支持逗号分隔任意 open_id）。
- 新增 `sync_user_materials(specflow_emp_base)`：遍历 `users[].scopes`：
  - 含 `minutes` → `minutes +search --owner-ids <open_id>` 按 `minutes_days` 窗口拉取落池（窗口上限 1 个月，超出按现有 days 语义截断）；
  - 含 `docs` → `docs +search --query "" --page-size 50` 搜当前用户可见文档 → 应用侧按 `owner_id == 目标 open_id` 过滤 → 逐条 `sync_doc` 落池（token 取 `result_meta.token`；wiki 类型 token 由 `docs +fetch` 自身按 token 路由处理，落池时 url 一并保存）。
- 轮询挂载：`FeishuWatcher._schedule_user_materials()` 挂 scheduler 每日 08:00（错开 07:00 文档轮询与 03:00 群聊校对）；job callable 必须模块级函数（APScheduler 可序列化铁律，闭包会炸 startup——三期经验包已登记）。

### 4.4 watcher 直写过滤（`feishu_watcher._direct_write_chat`）

在原逻辑前增加两道校验：

1. **chat 授权校验（D5）**：chat_id 不在 `watch.chats` → 直接丢弃（p2p 事件的 chat_id 天然不在列表中，兼容 D2）。
2. **发送人过滤（D4，仅直写）**：令 G = 所有 `scopes` 含 `group_sender` 的 `users[].open_id` 集合——G 非空时，仅 `sender_id ∈ G` 的消息直写；未命中不直写。每日 03:00 `chat_proofread_job` 校对重拉保持全量覆盖，不受过滤影响。

配置读取时机：每次事件处理时读取 watch 配置（与 `_throttled` 频次一致），保证保存配置后即时生效，无需重启子进程。

### 4.5 错误处理与边界

- 三个选择器端点：CLI 失败 → `{"items": [], "errors": [...]}`；前端红条展示，不阻断弹层其他区域。
- 用户文档检索的召回边界（2026-08-17 实测定案）：CLI `--filter owner_ids` 不被 Search v2 尊重，统一走**应用侧 owner 过滤**；空 query 搜索召回的是「当前用户可见的近期文档」（非目标用户全部文档），用户文档监听语义为「召回 ∩ owner 匹配」，边界在前端提示中诚实说明。
- watcher 过滤逻辑所有异常仅记 warning 日志，不阻断事件循环。

## 5. 前端设计（`FeishuReviewPanel.tsx` 同步设置弹层升级）

- **群聊区**：打开弹层时调 `GET /feishu-pool/chats` → 多选列表（群名 + chat_id），已授权的默认勾选；保留手填 textarea 作为兜底（粘贴 chat_id，保存时与勾选合并去重）。
- **用户区**：搜索框（姓名/邮箱）→ `GET /feishu-pool/users` 结果列表（姓名/邮箱/部门）→ 点击加入已选列表；已选用户列表每人一行，勾选监听范围 `群消息 / 妙记 / 文档`（对应 scopes）；行尾可移除。
- **文档区**：保留 token 手填 textarea；新增「按用户搜文档」——选定已选用户 + 关键词 → `GET /feishu-pool/user-docs` → 结果勾选加入 docs（回填 token/url/owner_open_id）。
- **保存**：组装 `FeishuWatch`（chats/docs/users/minutes_days/chat_days）→ `PUT /feishu-pool/watch`；保存成功提示沿用现有 notice，watcher 状态沿用现有返回展示。
- **类型**：`api.ts` 扩展 `FeishuWatch`（`users: FeishuWatchUser[]`、`chats[].name?`、`docs[].owner_open_id?`）+ 三个选择器 API 方法。

## 7. 非目标与边界

- 私聊（p2p）监听本期不做（D2）。
- 不改引擎冻结层（engine/）、specstd 规范层；无需三同步（引擎能力未变更），`release_check` 契约指纹不变。
- 不引入新依赖；lark-cli 命令面均为现有版本能力（已实测）。
- 用户妙记/文档的"事件级"实时性不做（事件侧 `minutes.minute.generated_v1` 仅覆盖监听账号自身妙记；指定用户妙记靠轮询，语义为每日级）。
