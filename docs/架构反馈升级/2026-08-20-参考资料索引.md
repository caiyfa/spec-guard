# LLM 智能体执行结果评测——基础知识盘点（specguard 评测体系缺口反馈弹药）

> 日期：2026-08-20 22:51
> 类型：query 存档（知识库盘点 + 体系化整理 + 缺口标注）
> 关联：[[Execution-based-Evaluation]] · [[EDD 评估驱动开发]] · [[LLM 输出评估]] · [[契约层反向校验]] · [[specguard]] · [[AI-Slop]] · [[Harness-Engineering]]
> 背景：specguard 智能层（agent/specflow）缺少对 Agent 执行结果的评测体系；用户正在另一会话进行相关反馈，需基础知识支撑。

## 一、TL;DR

知识库对此主题覆盖度约七成，四份核心资产：[[Execution-based-Evaluation]]（执行式验收=specguard 已有基因）、[[EDD 评估驱动开发]]（评估工程化三要素）、[[LLM 输出评估]]（维度/基准/盲法/统计四步方法论 + 陷阱清单）、[[契约层反向校验]]（验收反向校验契约）。**缺口**：过程/轨迹评估、LLM-as-Judge 独立成页、Agent 评测基准对照、pass@k 与非确定性处理。specguard 的正确路径不是"从零建评测"，而是**把已有的 oracle 模式从"接口返回值"扩展到"Agent 动作副作用 + Agent 文本产物"两类新对象**。

## 二、基础知识体系（评什么 → 怎么评 → 怎么组织 → 防什么坑）

### 2.1 评什么：Agent 评估对象三分法

| 对象 | 问的问题 | 例子 | wiki 覆盖 |
|------|---------|------|----------|
| **结果（Outcome）** | 最终状态对不对 | DB 状态变了没有、文件生成对不对、任务完成没完成 | ✅ [[Execution-based-Evaluation]]（ground truth 锚定） |
| **过程（Process/Trajectory）** | 走的路径好不好 | 工具调用选择对不对、参数对不对、有没有绕路/无效调用/循环 | ⚠️ 散见于 [[EDD 评估驱动开发]]，无独立概念页 |
| **成本（Efficiency/Cost）** | 花了多少代价 | token 消耗、步数、时延、$/run | ❌ 基本空白 |

业界共识（DeepMind Agent Evaluation 综述口径，confidence 0.7）：**结果评估是底线，过程评估区分"对的偶然"与"对的必然"**——同样完成任务，8 步直达与 30 步试错含 3 次幻觉调用，结果分相同但 Agent 质量天差地别。

### 2.2 怎么评：五种手段按可信度排序

| 层 | 手段 | 信号硬度 | 成本 | 适用 |
|:--:|------|:--:|:--:|------|
| 1 | **确定性检查**：JSON Schema/字段完整/数值范围/正则 | 硬 | 极低 | 结构化输出（specstd/conformance.py 就是这类） |
| 2 | **参考匹配**：关键词/语义相似度阈值 | 中 | 低 | 有参考答案的半开放输出 |
| 3 | **执行式验收**：真实环境跑，环境反馈是唯一信号 | 最硬 | 中 | 有副作用的动作（DB/文件/API 调用）；**抗 AI-Slop 根本手段** |
| 4 | **LLM-as-a-Judge**：强模型按 rubric 评分 | 软 | 中高 | 开放文本质量（摘要/释义/面试记录） |
| 5 | **人工评估**：双盲+统计检验 | 金标准 | 最高 | 校准层——校准 Judge 本身，非日常批量 |

关键原则：**能用 1 不用 2，能用 3 不用 4**；5 不是常规手段而是"评估的评估"（meta-evaluation）。

**LLM-as-a-Judge 要点**：
- 形态：pointwise 打分（配 rubric）/ pairwise 二选一（更稳）/ listwise 排序
- 已知偏差：**自评分偏差**、位置偏差、冗长偏好、近因偏差
- 前提动作：**先验证 Judge 与人工标注的一致性**（抽样对账，一致率/κ 达标后才允许 Judge 上量——即 meta-evaluation）
- 抑制手段：评分与生成模型分离、rubric 操作化定义、多 Judge 投票、强制引用证据段

### 2.3 怎么组织：EDD 三要素（评估工程化）

1. **Eval Set**：从 3 个 gold case 起步；每次线上问题转为新 case；覆盖正常/边界/已知失败；**与代码同版本控制 = 行为契约**
2. **Eval Function**：按 2.2 五层组合，优先确定性
3. **回归机制**：prompt/模型/Agent 逻辑任何变更后重跑全量 eval set，通过率降 → 回滚；目标是"5 分钟知道退化，而非等用户投诉"

飞轮：**线上问题 → 新 eval case → 优化 → eval 验证 → 上线**。

**非确定性处理**：同一 case 跑 k 次（pass@k / 成功率而非单次 pass/fail）；评估期固定 temperature/seed；区分"能力失败"与"随机波动"需要多次采样做统计。

### 2.4 防什么坑：陷阱清单

| 陷阱 | 一句话 | 解法 |
|------|--------|------|
| 自评分偏差 | 生成者≠评分者 | 模型分离 |
| 时点不对等 | 基准与被评对象的信息时点不齐 | 对齐信息时点 |
| 维度等权假设 | 各维度 1 分但实际权重不同 | 解读时声明假设 |
| 强制二选一 | 真实评估"并列"是常态（实测 19%~50%） | 引入并列 0.5 |
| AI-Slop ≠ 幻觉 | slop 看起来对但没价值；执行式验收两个都能抓 | 环境反馈验收 |
| 统计缺位 | 均值差异不过显著性检验只是感觉 | 配对 t / Wilcoxon，p<0.05 |

### 2.5 业界坐标系：评测基准

| 基准 | 评什么 | 验收方式 |
|------|--------|---------|
| SWE-bench（2310.06770） | 真实仓库 issue 修复 | 跑测试套件，resolve rate |
| AgentBench（2308.03688） | 8 环境 11 应用综合 | 环境内任务完成 |

## 三、specguard 视角：已有的基因与缺的三层

### 3.1 已经有的（别推倒重来）

| specguard 现状 | 对应方法论 |
|---------------|-----------|
| engine 的 verify 双层断言（json + oracle）+ DB 快照 ground truth + 权限预言机 | [[Execution-based-Evaluation]] 系统级实现——**结果评估的执行式验收已是强项** |
| reports/ 轨迹证据（HTTP 轨迹 + db_traces + run.json） | 过程评估的**素材已在落盘**，缺的是评估函数 |
| specstd/conformance.py（合规校验）+ lineage（断链规则 BL-01~06） | 确定性检查层已成型——对"规格产物"的确定性评估 |
| graph_index 指纹失效重建 | 派生数据一致性自检 |
| feedback/ SPQ 台账 | 反哺闭环的记账侧（EDD 飞轮的"问题收集"半边） |

### 3.2 缺的三层（建议方向）

1. **Agent 文本产物评估层**：智能层产物（面试记录/决策台账/spec 草案/摘要）目前没有 eval 函数。按 EDD 分层套：schema 确定性检查（conformance 基础上扩）→ 参考匹配 → LLM-as-Judge（先做 Judge 与人工抽样一致性校准）
2. **轨迹评估层**：agent/session.py 的 JSONL 会话已是完整轨迹，定义评估函数：步数、工具调用成功率、循环/重试检测、token 成本、无效调用率——这是 [[Agent-Loop]] 的"过程质量"量化
3. **回归机制层**：eval set 入库（gold case 起步，feedback 台账的问题转 case），prompt/skills/模型变更触发重跑——把 feedback 的另一半飞轮补全

一句话定位：**specguard 会测"别人的系统"（被测系统 TDM），还没测"自己的 Agent"（智能层）——把 oracle 思想从对外测试反身应用到智能层产物上。**
