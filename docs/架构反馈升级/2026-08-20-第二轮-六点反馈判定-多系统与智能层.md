## 1. 多系统设计意图：成立，但"单系统残留"是接第二个系统前的真实账单

**用户反馈原文**：「系统肯定不是单独给TDM这个系统单独设计的 只是用它来测试的，后期肯定会接入很多其他系统的」

**事实**：多系统在**工作区注册这一半链路成立**（`WorkspaceInfo.system` 字段存在，specstd/workspace.py:148；plan_executor.py:133、scenario_tools.py:427、runs.py:175、knowledge_service.py:45-50、agent/runtime.py:582 均尊重它），另一半链路仍是单系统假设（详见第 2 点断链清单）。加上引擎内 TDM 泄漏三处：`http_client(account, service="tdm")`（scenario_runner.py:126）、`default_resource_code: "TDM_SNAPSHOT_ARCHIVE"`（:120）、HR 中文词库 `RANDOM_POOLS`（:521-549）。

**判断**：不是设计错误，是"只有一个租户时没人踩到"的典型残留。但它决定了**接第二个系统的第一步不是写新适配包，而是先把 system 做成一等公民**，否则新系统接进来会在半条链路上"看不见"。

## 2. "系统注册"：不同意做注册 CRUD，同意做"系统一等公民化"（2026-08-21 修正：分级开放——配置型系统做 UI 注册+热加载，代码型系统评审闸不绕）

**用户反馈原文**：「当前是否缺失了系统注册功能，目前都是围绕工作区进行的」

**实测现状**——系统注册以三种形态**存在**：
1. 代码级插件契约：`systems/{system}/` 包 + `register(registry, env_config, db)` 钩子 + importlib 装配（conftest.py:117-121、systems/tdm/__init__.py:6-25），AGENTS.md:270-278 有接入契约文档；
2. 运行时目录枚举：`workbench/backend/services/systems_catalog.py:19-43` `list_systems()` 扫描 systems/ 下非 `_` 开头目录；`GET /api/workspace/systems`（routers/workspace.py:118-121）供注册表单下拉；
3. 工作区绑定：`WorkspaceInfo.system`（多对一），router 层 `_validate_system` 校验（workspace.py:49-51）。

**SPEC_GUARD_SYSTEM 全部读取点（9 处，无任何代码写入该变量）**：

| 位置 | 解析顺序 |
|---|---|
| conftest.py:47（sg_system fixture） | 仅环境变量 |
| mcp_server/tools/live_registry.py:32 | 仅 env，**且进程级缓存**（_CACHE :20/:51） |
| mcp_server/tools/attribution.py:398 | 仅 env |

| runner.py:123（通知推送） | 仅 env |

**断链清单（反馈属实的部分，按严重度）**：
1. **bug 级**：`runner.py:80` `_spawn_pytest` 构造子进程环境只加 SG_ENV，**不按触发工作区注入 SPEC_GUARD_SYSTEM**——RunControl → POST /api/runs/trigger → pytest 子进程这条主执行路径永远跑后端进程 env（默认 tdm），工作区绑定的 system 形同虚设。
2. preflight：runs.py:162 调 scan_dependencies 不传 system，退回环境变量（docstring :215 声称"默认工作区"与实现不符）。
3. live_registry.py:32 / attribution.py:398 / data_validator.py / runner.py:123 均 env-only——多系统部署下这些能力锁死单系统；live_registry 缓存后无法切换。
4. reference.py /envs 端点 env 列表硬编码 `systems/tdm/config`；`scenario_store.py:22` SCENARIOS_ROOT 固定仓库根（不感知工作区），与 plan_executor 的 `{工作区}/scenarios` 口径不一致。
5. 无独立"系统管理"页面/路由——system 在 UI 里只是工作区注册表单下拉（WorkspaceCenter.tsx:323-331）与卡片徽标、EnvironmentConfig 的系统选择器（:31-35,109-116）。
6. system 没有 contextvar（workspace 有 `_CTX_WORKSPACE`，system 没有），9 个调用点各自解析、顺序不一。

**判断**：
- ~~缺运行时"系统 CRUD 管理面"不是缺口：适配包含代码（steps/oracles/env），本质只能代码级诞生——与业界插件架构一致（插件 = 放代码 + 自注册），给系统做 UI 创建/删除是伪需求。~~
  > **【2026-08-21 修正·用户推翻】** 用户不接受"每接一个系统都要开发改代码+重启后端"。复验加载机制后修正为**分级方案**：
  > - **重启是实现事故不是架构要求**：注册动作本身已动态（模块导入时 register_tool/mod.register，零硬编码清单），硬点只有三处——①系统包必须躺在仓库 systems/ 目录 ②live_registry 进程级缓存 + prod workers=1 不热重载 ③env 配置与 Python 代码捆在同一包内，纯配置系统也被迫建包。
  > - **诚实分界**：环境配置/账号池=纯数据、通用 DB 校对=可模板化（SQL+断言模式），这两类**零代码即时接入**成立；专属 steps/oracles=任意 Python（exec），与 ENG-SEC-001 同类，**永远不可能免评审**——能做的是"评审后热加载免重启"，不是"免评审"。宣称"任何系统纯配置接入"的设计最终都是把 Python 换成伪装成配置的表达式语言，安全性更差。
  > - **目标设计（系统包 system package）**：`{SG_SYSTEMS_ROOT}/{system}/`（可在仓库外）= manifest.yaml + env.{env}.yaml + assertions.yaml（声明式断言模板，可选，零代码）+ extensions.py（专属 steps/oracles，可选，=可执行代码）。加载器按文件位置 importlib 加载、按 system 分键缓存可单系统失效重建——**P1-1 的缓存分键修复恰是热加载接缝、P1-2 装配归一恰是唯一加载入口**，两任务顺势完成。三级接入：①纯配置→UI 注册/编辑/启停即时生效；②模板断言→同①+确定性校验器（复用 db_oracle SELECT-only 守卫）；③代码型→上传落"待评审"，admin 评审通过激活即热加载（评审留痕：谁审的+文件 sha256）。配套必修：tool_registry.TOOLS 全局字典改 `system:name` 命名空间防热注册撞名（本属 P1-1 范畴）。
  > - 修正后表述：**「代码型系统不做 UI CRUD（评审闸不可绕）；配置型系统开放 UI 注册+全量热加载」**。接第 N 个系统的目标形态：从"开发排期"变"配置半天"。
- **真缺口三件事**：① system contextvar 或统一 `resolve_system()`（所有调用点归一）② 执行链贯通（修 runner 注入、live_registry 按 system 分键缓存、preflight 传 system、reference 去硬编码、scenario_store 口径统一）③ ~~只读系统清单页~~ → 系统包注册面（分级：配置型 UI 可建，代码型评审激活）。
- 准确表述：「一切都是工作区」的感觉来自 **system 不是一等公民**，而不是缺注册功能。

## 3. 飞书多群交叉：缺口属实，且是设计层就没建模

**用户反馈原文**：「缺少多个群聊记录交叉验证话题的功能，因为一个系统相关的话题肯定不止一个群，有测试群 迭代群 产研群 用户群 项目群 运维群等等」

**实测——三层全缺，全仓 grep `跨群/多群/交叉验证/cross_chat` 零命中**：

1. **数据模型层**：话题卡只有单值 `chat_sha8` 和单文件 `source`（facts.py:23-26）；话题 id 方案 `tp:{chat_sha8}-{day}-{seq:02d}`（topic_cluster.py:238）**把群哈希编码进身份，结构性阻止跨群归并**。watch 配置群条目只有 chat_id/name/topic_days 三字段（api.ts:1648），无群类型语义；群名不落盘，读取时从 watch 反查（feishu_sync_service.py:602-608）。
2. **聚类算法层**：`cluster_chat_snapshots` docstring 明示"按「群×天」逐文件独立聚类"（topic_cluster.py:242-249，双层循环 :280-293）；演进链只在同群（`_existing_topics_digest` :54-62 过滤 `t.get("chat_sha8") != chat_sha8`）；归并 `_merge_one` 要求同群+同日+标题相似度≥0.6（:221-239）——跨群相似话题各拿新 id 互不合并。
3. **展示层**：TopicWorkspace.tsx:344-349 顶栏强制"先选群"，话题按 `t.chat_sha8 === sha8` 过滤（:237）；无全局话题列表、无跨群交叉引用 UI。多日窗口 days（T-951c）也是同群跨日。

**link_suggest 一次一份材料正文**（link_suggest.py:66-112，话题只传 summary）×FR 锚点目录——不存在"一个话题聚合多群多材料证据"的模型。设计文档（T-948 §2.3 话题卡 schema v2）设计层面就是单群口径。

**判断与增量路径**（跨群归并是 hard problem——同主题不同群表达差异大、时间线错位，不建议一步做"交叉验证"）：
1. **先交叉可见**：watch 群条目加 `kind`（群类型）标签（轻）+ 话题卡加 `source_chats` 聚合字段 + "跨群相似话题关联"阶段（相似度只做关联推荐，不做自动合并——复用现有 draft→commit 人工介入模式，该模式仓里已打磨得很好）。
2. **再交叉印证**：多群证据并排视图 + link_suggest 从"单材料正文"升级为"多来源证据集"。
3. 群类型语义先落在 watch 配置与展示标签，不急于参与聚类算法。

## 4. 测试类型学：属实——但"应搓出来的引擎"自评只对一半

**用户反馈原文**：「针对单一场景测试没有分类聚类，比如测试查询条件有效性、测试数据权限、测试增删改接口是否真实落库……需要符合专业测试人员的常识和企业级标准，目前感觉就是应搓出来的测试引擎，毕竟我是一个开发」

**实测（场景库 24 个场景文件全量统计）**：
- 顶层字段：id/title/version/priority/tags/doc/flow/verify/depends_on 全有；`test_type` 仅 9 个文件有（取值 scenario/unit），且格式规范 2.4.0 已废弃（format_spec.py:40"unit/scenario 二分抹除"）——**此后再无类型建模**。
- tags 实际值 16 个：resolver(7)/negative(4)/import(4)/revert(3)/snapshot(2)/security(2)/row-isolation(2)/prep(2)/permission(2)/grid(2)/eval360(2)/session-lifecycle(1)/revert-base(1)/import-base(1)/requirement-driven(1)/regression(1)——"业务域词+执行角色词+测试性质词"混用的自由词表，无受控枚举，validator 不校验。
- **真 bug**：`test_scenarios.py:32-38` 只把 tags 转 pytest mark，priority 从不注入（scenario_loader.py:159-160）——文件头注释宣称的 `pytest -m P0` **实际选不中任何用例**（无场景 tags 含 P0/P1）。
- 覆盖率：covers_gate.py:17-39 只校验 FR 锚点覆盖；coverage_gaps 三态聚合坐标轴是 FR×场景×草稿；CoveragePanel 纯 FR 维度；list_scenarios 只有 by_module/by_tag——**全仓无"按测试类型统计"痕迹**。
- 生成技能 generate-scenario.md（132 行）：零测试设计方法论（无等价类/边界值/权限矩阵/落库断言模式），只有流程编排/DAG 设计/权限预检/格式硬约束。audit-spec.md:20 的"边界条件"是审 spec 的 checklist 不是测试方法。

**判断**：**引擎骨架不是"应搓"的**——双层断言（json+oracle）、DB 快照 ground truth、权限预言机、SKIP 诚实语义，对应业界执行式验收是系统级实现。真正缺的是**测试设计知识层**（"专业测试人员拿到一个 FR 会想到测什么"的领域知识没编码进系统）。参照 ISTQB 四分类（功能/非功能/结构/变更相关）与 CMU SEI 测试分类学，建议：
1. **受控测试维度词表**进 doc 层（如 `dimensions: [query-validation, data-permission, crud-persistence, boundary, negative, idempotency, regression]`）——用户举的三个例子正好对应前三个值；validator 校验、按维度聚合进覆盖面板；走引擎能力三同步纪律（format_spec+版本号+契约指纹）。
2. **维度→断言模式映射**：crud-persistence ⇒ 应含 db_query/oracle；data-permission ⇒ permission 类 oracle；negative ⇒ 期望非 2xx——validator 做确定性检查（"标了落库维度却没有 DB 断言"告警）。
3. **生成技能注入测试设计方法**：按 FR 类型建议维度组合（权限类 FR→权限矩阵正反例；查询类→等价类+边界值；写操作→落库断言）。
4. 顺手修 P0/P1 mark 断链 bug。

## 5. Agent 评测体系：完全属实，wiki 文档框架背书 + 最低成本落地路径

**用户反馈原文**：「关于LLM Agent 缺少测试体系，一个场景有没有调用指定工具、skill，最终执行结果如何，都是靠我手动测的。没有标准评价体系」
**参照文档**：用户 wiki《2026-08-20-2151-agent执行结果评测基础知识.md》（全文转录见参考资料索引）。

**实测**：
- 已有两层：①harness 机制单测（test_specstd/test_agent.py 1274 行，MockLLM 可配置响应序列——验证循环/熔断/持久化/隔离，**不是任务级评测**：无 golden case、无轨迹比对、无任务成功率）②纯 token 计量（llm_client.py:346-363 每轮一行 {timestamp/model/prompt_tokens/completion_tokens/total_tokens/cache_hits/misses}，无工具维度；消费方仅 3 个单点：session.py:343-352、inspect.py:128-138、routers/agent.py:881）。
- `--mock` 机制：agent/cli.py:27,32 → llm_client.py:365-372 `_mock_chat` 固定回显一句"[MOCK]…"无 tool_calls 即停——**既不能编程扮演"会调工具的 LLM"，也不 mock 工具结果**，只能验证 runtime 空转。
- 产物自动评估：场景草稿 validator 全是格式与引用合规（T1/T4/T5/T6/T8/COVERS/REGISTRY 幻觉拦截）；三闸中 gate1=人工评审；**specflow/anchor/scoring.py 五维评分（logic/clarity/coverage/boundary/precondition）是仓内最接近自动评估的资产，但不在 agent 对话链路上**。
  > **【2026-08-21 勘误·翻案】** 经知识库会话独立核验并在本仓复验：scoring.py **已在链路上**——`sf_suggest_scores` 工具经 `mcp_server/tools/specflow_ledger.py:164` import `collect_all_machine_dimensions` 并注册进 MCP server（`server.py:35,80`）。真相比"没接入"更糟：机打四维（logic/coverage/boundary/precondition）已由真实采集器驱动，**但 clarity 维度仍是硬编码占位常量 62.0**（`specflow_ledger.py:179`，evidence 文案"LLM 建议：预期清晰度待 QA 复核"），以正常评分形态入库。缓释因素：status=`suggested` 不计入总分、需 QA 确认才生效（`decision_service.py:117-126`），但 QA 不逐条核对 evidence 即可能确认假分数。原判定"不在链路上"作废。
- 全仓文件名搜 eval/benchmark/regression/golden/replay：**第一方零命中**；根目录 `_analyze_session.py` 硬编码会话路径的一次性脚本正是"手动测"的铁证；session.py:356-376 导出 summary 有 tool_calls 计数与 error_count 但无跨会话聚合/成功率/看板。

**判断与落地路径**（背书 wiki 文档"把 oracle 思想从对外测试反身应用到智能层产物"）：
1. **轨迹评测先行（成本最低收益最快）**：JSONL 已完整落盘（素材不缺，缺评估函数）；test_agent.py 的 MockLLM 本就支持可编程响应序列——提升为正式 eval 基建：golden case =「任务 prompt + 期望工具调用序列（或子集）+ 产物断言（复用 validator）」，scripted-LLM 驱动离线回放。直接回答"调没调指定工具/顺序对不对"。
2. **结果评测接现有资产**：validator 已是确定性检查层；scoring.py 不必新建、但**也不是"接入即可"——先清理链路上的 clarity 假分数**（specflow_ledger.py:179 占位常量 62.0：要么 LLM 真评、要么诚实降级为"待人工评分"不入库），再谈作为评测资产复用。
3. **回归机制**：evals/ 目录入库（3 个 gold case 起步，EDD 原则）+ feedback 台账问题转 case（记账侧已有，补飞轮另一半）+ prompt/skills/模型变更触发重跑。
4. LLM-as-judge 与 pass@k **后置**——五层原则"能用 1 不用 2，能用 3 不用 4"，确定性轨迹断言没穷尽前不上软评估。

## 6. 工具收敛：属实，已踩量化红线，收敛基建一半已在

**用户反馈原文**：「关于工具需要进行提炼，控制工具的数量，得按领域进行分类合并」

**量化证据**：业界实测——候选池 <30 工具选择准确率 >90%，超阈值骤降（有报告降到 13.62%）；从业者经验 ~15 个为宜；超 ~40 个模型会混淆工具名、幻觉参数。SpecGuard 现在 **29 模块 92+ 工具全量注册**——超阈值 3 倍，是当前 agent 质量问题的可疑主因之一（值得与第 5 点评测体系联动验证：收敛前后跑同一 eval 集对比）。

**收敛路径**（方向同意，补三点）：
1. **合并 CRUD 碎片**为参数化工具（list/get/search 用 action 参数合一），按领域分组（scenario/spec/draft/validate/attribution/audit/graph/feishu/zentao）。
2. **动态暴露**：runtime 已有三层白名单（resolve_tools :144-166 = 全注册∩purpose∩RBAC）——基建在，问题是"全注册"池太大。默认暴露改为"按会话任务类型选领域子集"，目标**单会话可见 ≤15、对内全集 ≤30**。
3. **两个既有问题随合并一起解**：runtime.py:59-118 的 70 行手工 RBAC 清清单改为从工具元数据派生；`_KNOWN_WRITERS` 手工写工具清单（side_effect_registry.py:31-69）改为在 Tool(...) 定义上声明副作用属性。注意 AWS 指出的合并代价——单工具 schema 变宽，命名要保住语义分辨率，不是越少越好。
