## 背景：三点反馈与现状证据

总控人反馈（2026-08-21）：

1. **工作区管理应让用户自行管理**——产品、测试、研发都能开自己的工作区，不该 admin 专属。
2. **需要「系统 → 工作区」二级选项**——现在注册新系统的工作区被校验卡住，页面也只有平铺的工作区一级选项，没有「一个系统多个工作区」（像 git 一库多 worktree）。
3. **产出物反查缺位**——过程文档对会话依赖太重，没有按产物/人/时间反查的地方，只能在 agent 对话里自己翻。

### 现状证据（已实测）

| 反馈点 | 现状 | 证据 |
|---|---|---|
| ① 自管理 | **注册接口锁 admin**：`register-local`/`register-git` 用 `require_role("admin")`，普通用户无法注册 | `workbench/backend/routers/workspace.py:123`（`api_register_local(... require_role("admin"))`） |
| ① 自管理 | **系统适配包硬校验**：注册时 `validate_system` 要求 `systems/{system}` 包必须存在，否则 400——产品/测试开工作区写 spec 前被迫先建 engine 包 | `workbench/backend/services/systems_catalog.py:112-121`（`package_dir(system).is_dir()` 不存在即 400） |

| ② 二级模型 | 数据层一系统多工作区**本就成立**（注册表已有 tdm + 人才发展两个 `system: tdm` 工作区），缺的是展示层分组与校验层放宽 | `specstd/workspaces/registry.yaml` |

| ③ 反查 | 草稿→场景仅有血缘 sidecar（promote 后写信息包），无反向「这产物是哪次会话/运行产出的」索引 | `sg_core/draft_promote.py:209` |

## 目标（三句话）

1. **工作区自管理**：登录用户（产品/测试/研发）可注册/激活/管理自己的工作区；系统字段与 engine 适配包解耦，写 spec 不强制先建包。
2. **系统 → 工作区二级**：选择器与工作区中心按系统分组、二级选择；一系统多工作区并列可见可切换。
3. **产出反查**：建立产出物索引，产物可溯源到产出会话/工号/时间/关联 FR；「我的活动」页让本人看见自己的会话/工具/执行/草稿记录。

## 方案设计

### F1 工作区自管理（①）

**模型改动：工作区与系统包解耦**
- `Workspace.system` 允许为空或指向「未建包」状态；注册时不再硬校验系统包存在。
  - `validate_system` 放宽为**软校验**：系统包不存在不 400，工作区照常注册，标记 `system_pending=True`（待接入）；跑测试/resolve_system 时才要求适配包就绪（T-971 的 resolve_system 已有诚实降级口径，复用）。
  - 合规校验（conformance）闸门**保留**——它是 spec 质量防线，与自管理不冲突。

**RBAC 改动：注册/激活放开给登录用户**
- `POST /api/workspace/register-local`、`/register-git`、`/activate`：由 `require_role("admin")` 放宽为「登录即可」（`get_current_user`），注册人记入 `owner_emp`。
- 权限边界：用户可见/可管理**自己的**工作区 + 被授权的工作区（沿用现有 `api_list_workspaces` 的 admin/授权过滤逻辑，:92-95）；注销/改他人工作区仍 admin。
- 审计留痕：`user_store.audit(emp, "register_workspace", ...)` 已有，注册人变更同步记。

### F2 系统 → 工作区二级模型（②）

**后端**
- `GET /api/workspace/list` 响应按系统分组（或新增 `GET /api/workspace/tree`）：`[{system, display_name, workspaces: [...]}, ...]`，未分组/无系统的归入「未绑定」组。
- 复用 `GET /api/systems`（T-973 已落）取系统目录做分组键与展示名。

**前端**
- **WorkspaceSelector（顶栏）改二级**：第一级选系统（含「未绑定」），第二级选该系统下工作区；选中写 `X-SG-Workspace`（沿用现有 header 机制，全页联动不变）。
- **WorkspaceCenter 重做上半部**：按系统分组的工作区卡片墙——每系统一组，组内并列该系统全部工作区卡片（名称/owner/spec 覆盖/草稿数/最近执行/激活按钮），像 git 分支列表一样并列；下半部文档浏览区保留不动。

### F3 产出反查（③）

**产出物索引（轻量，落 workbench.db 新表 `product_index`）**
- 字段：`{product_path, product_type(draft/scenario/plan/...), session_id, emp_no, created_at, fr_anchor, workspace}`。
- 写入点：agent 写草稿、promote 入库、计划生成、场景保存处各插一条（钩子挂在既有写路径，不改引擎语义）。
- 反查接口：
  - `GET /api/products/by-session/{sid}`——某会话产出了什么；
  - `GET /api/products/mine?emp=&type=&from=`——我的产出（本人查本人，非 admin 可用）；
  - `GET /api/products/trace?path=`——产物溯源（这草稿/场景是哪次会话/运行产的）。

**「我的活动」页（前端新页，本人可见）**
- 按当前登录 emp 过滤：我的 agent 会话列表（点进去看消息链，读 `agent/sessions/{emp}`）、我的工具调用、我的场景执行历史、我的草稿/产出。
- 后端 audit 查询放开「本人查自己」：`emp == 当前用户` 时不强制 admin（audit.py 现有过滤逻辑加本人分支）。
- 产物详情页（草稿/场景）加「溯源」入口跳产出会话。
