## 1. 菜单信息架构审计

**用户反馈原文**：「目前的菜单目录是否存在很多多余的菜单，在正常的用户工作流里面不会被用到，或者一个功能硬拆成独立菜单提升了用户的学习成本，我更倾向于将对应功能拆成agent对话时右侧面板内容，真有必要独立菜单的也得能自成体系。现在很多菜单能力都很鸡肋，功能丰富度不够，深度广度都不够，只是简单的增删改查的菜单就标榜自己实现了什么功能」

### 1.1 导航结构与 RBAC 事实

- 抽屉式侧边栏（App.tsx:193-290）；菜单数据非代码写死，登录后 `menusApi.me()` 动态拉取（App.tsx:137-144）；路由守卫：path 不在可见菜单 → 🔒 无权限页（:158-166,336-341）。前端 32 条 Route（30 实页 + 2 Redirect）。

- admin 专属：menu-users/menu-menu-manage is_system=1（:43,45）；AuditLog require_role admin（audit.py:24,44）。日常高频：Agent 对话 + RunControl + Drafts + DAG。
- Home（99 行）是导航枢纽页（问候+CTA+navTree 卡片网格，零数据请求）；Dashboard（302 行）才是数据总览。

### 1.6 判断（含两处保留意见）

- **同意"薄 CRUD 页降级为面板/页签"**，但判据明确成规则：**"目的地"页面留菜单**（用户专程去完成一段完整工作：画布/流式日志/三道闸评审——DAG 718 行画布、RunControl 791 行 WS 流式、Drafts 585 行三闸双模，面板装不下）；**"伴随动作"进 AgentChat 右侧**（对话过程中确认/勾选/入包的动作——材料、评分、冻结、话题确认、禅道建故事，正是操作台已有的那批）。与业界企业导航方法共识一致：导航对齐用户任务模型，顶层菜单宜少、按任务域分组。
- **保留意见一：管理配置页不删，收进低频区**。AdminUsers/MenuRoles/AuditLog/EnvironmentConfig/Settings 是 admin 受众低频页，"CRUD=鸡肋"对管理页不成立（管理页本分就是 CRUD）——聚成一个"系统管理"分组即可。
- **保留意见二：先拆 AgentChat.tsx 再加面板**。它已 3954 行、102 个 useState，全仓最大前端文件；面板注册机制是好的，宿主文件超载。往里塞面板之前应先把 SidePanel/对话区/会话树拆成独立模块，否则是把债务从菜单搬进文件。

## 2. 话题分类现状与设计建议

**用户反馈原文**：「对于话题分类，目前都是打标签形式，缺少固定的分类：闲聊话题、正常沟通话题、需求相关话题、测试相关话题、方案相关话题，话题涉及的功能模块，还有话题优先级」

### 2.1 现状穷尽（实测）

**话题卡 17 个字段全集**（facts.py:23-26 `_TOPIC_KEY_FIELDS`）：id/title/summary/keywords/chat_sha8/window/message_ids/message_count/participants_count/source/continues/status/author/rev/agent_origin/last_edited_by/last_edited_at——**没有 category/priority/module/severity 任何一个**。全 feishu_pool grep `category|priority|severity|classification|module` 唯一命中是 link_suggest.py:39-47 的 FR 锚点目录属性（非话题字段）。设计文档 T-948 §2.3 schema v2 与代码一致。

现有全部"分类"手段（穷尽）：
1. `status: draft|confirmed|rejected`（topic_cluster.py:31 枚举）——人工生命周期，非内容语义分类；edit_candidate 只允许编辑 title/summary/keywords（:643-681），PUT /topics/card 同（routers/feishu_pool.py:294-300）。
2. `keywords: list[str]`——LLM 生成/人工可编辑的自由文本标签，**仅卡片展示（TopicCard.tsx:155-163），不进图谱（builder.py:359-366 连 keywords 都不带）、不参与检索/筛选/排序**。用户的"打标签"观感准确。
3. prompt 层二分过滤：聚类 prompt 规则 1「只聚类有实质讨论内容的消息（需求/方案/决策/问题）；**闲聊（吃饭问候等）不聚类**」（topic_cluster.py:39）——**闲聊是被丢弃，不是被分类**；_DRAFT_PROMPT :362 同款；_REGEN_PROMPT :458-466 完全无分类指令。
4. 间接关联：话题经复核确认的 mentions 边连 FR，再经 FR→feat→mod contains 边间接通达模块（builder.py:481-482）——但见下。

**🔴 另发现一个生产死链**：`link_suggest.suggest_links_for_material`（话题→FR 锚点关联建议，三重防幻觉 :93-111）与 `enqueue_suggestions`（feishu_review_service.py:55）**在生产代码中零调用**——只有测试在调（test_feishu_sync.py:359-366）；同步服务只触发聚类（feishu_sync_service.py:318），watcher/sync 不触发建边建议。"话题涉及哪个功能模块"本来有一条设计好的路，但链路断着。

**前端**：TopicCard 无分类/优先级/模块展示；TopicWorkspace 唯一筛选 statusFilter（all/draft/confirmed/rejected，:66/:242-250），泳道 `assignLanes` 按 window 时间排序（:21-41）——**排序维度是时间，不是优先级**；FeishuPool 只统计候选/已确认数。api.ts FeishuTopic 类型与后端白名单一致。

### 2.2 设计建议（同意五分类，补三个设计决策）

1. **固定分类枚举** `category: chat | routine | requirement | test | solution`（对应闲聊/正常沟通/需求/测试/方案）。两个要点：
   - **闲聊从"丢弃"改为"分类后默认过滤"**——纯丢弃依赖 LLM 单次判断且不可审计（边界案例丢错无据可查）；分类保留后默认视图隐藏，多一个字段换来可审计性与群噪声率信号。
   - 枚举必须有**操作化定义（rubric）+ few-shot 示例**写进聚类 prompt——封闭集分类可靠性完全取决于定义清晰度（与测试维度受控词表同理）。
   - status（生命周期）与 category（语义）正交，别合并。
2. **功能模块不新增自由文本字段，走 FR 锚点派生**：修复上面的死链（同步后触发 enqueue_suggestions → 人工复核确认 → mentions 边），话题模块 = 关联 FR 锚点经 mod: contains 边派生。理由：FR→模块目录已存在且被 covers 门禁维护；话题侧自由文本 modules 是第二个要人工维护的词表，必然漂移。关联不到 FR 的话题（闲聊/日常沟通）模块留空，语义自洽。
3. **优先级信号推导而非纯 LLM 拍脑袋**：初值 = f(关联 FR 的 P0/P1、参与人数、消息量、来源群类型)，LLM 可微调、人工可改（复用 edit_candidate 机制）；`priority: high|normal|low`；前端接进泳道排序与筛选（现在只按时间）。

**schema v2 → v3 改动面清单**（一次演版做完，别分两次）：`_TOPIC_KEY_FIELDS` 白名单、聚类/draft/regen 三个 prompt 输出 schema + `_PROMPT_VERSION` 升版、`_normalize_card` 存量卡补默认值、`edit_candidate`/PUT /topics/card 可编辑集、`FeishuTopic` 类型、TopicCard 徽标、TopicWorkspace 筛选排序。

**与第二轮反馈联动**：群类型标签（测试群/产研群）是话题分类的强先验（测试群里的话题大概率 test 类），实现成本最低——排序：**群类型标签 → 话题 category/priority → link 死链修复与模块派生 →（远期）跨群话题关联**。分类做好后的红利：test 类话题可作为场景生成素材入口（分类筛选后的测试讨论喂给 generate-scenario），把材料池和场景体系接起来。
