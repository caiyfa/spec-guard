# 引擎升级建议 · 第三批 —— 对标开源执行引擎能力评估

> 2026-08-06 调研。目的：对照主流开源 API 场景测试引擎（Karate / HttpRunner / Tavern / Schemathesis），评估 SpecGuard 执行引擎（格式规范 v2.4.0）是否需要升级、升级什么。
> 前两批见 `docs/引擎升级建议-DB断言与异步轮询.md`（U-1~U-5）、`docs/引擎升级建议-第二批-变量插值与资源命名.md`（REQ-1~REQ-4）。

---

## 一、总结论

**不需要颠覆性升级。** 引擎的变量/提取/断言链、轮询、共享上游、DAG 依赖调度、DB 断言、诚实 SKIP/BLOCKED 语义已对标甚至超越主流 YAML 场景引擎；其中「DAG 依赖 + 契约版本仲裁」是开源对标本里**没有**的独有能力。

识别出 **6 项能力缺口**，建议按 P1/P2/P3 分级补齐；另明确 3 项「不建议做」。

## 二、对标矩阵

| 能力 | SpecGuard | Karate | HttpRunner | Tavern |
|------|-----------|--------|------------|--------|
| 变量/提取/断言链 | ✅ `{{}}` 插值 + save | ✅ | ✅ | ✅ |
| 轮询 until | ✅ poll（仅 HTTP call） | ✅ retry until（任意步骤） | ⚠️ 弱（hook 实现） | ✅ delay/retry |
| 共享上游执行一次 | ✅ shared 实例池 | ✅ callonce | ❌ | ❌ |
| DAG 依赖 + 版本仲裁 | ✅ **独有** | ❌ | ❌ | ❌ |
| DB 断言 | ✅ db_query + oracle 注册表 | 需 Java interop | 需 hook | 需插件 |
| JSON Schema 结构校验 | ❌ 仅逐字段断言 | ✅ fuzzy match | ⚠️ jmespath 拼装 | ✅ schema 块 |
| 通用重试原语 | ❌ 仅 401 单次重取 | ✅ retry until | ❌ | ✅ |
| 数据驱动参数化 | ❌ | ✅ Scenario Outline / CSV | ✅ parameters | ✅ parametrize |
| 并行执行 | ❌ 串行 session | ✅ parallel | ✅ pytest-xdist | ✅ pytest-xdist |
| 场景级超时 | ❌ 仅请求级 timeout | ✅ | ✅ | ✅ |
| 契约 fuzzing | ❌ | ❌ | ❌ | ❌（Schemathesis 独立工具） |

## 三、能力缺口清单（按优先级）

### P1-1 通用重试 / DB 轮询

- **现状证据**：`poll` 步骤只接受 `call + until`（`engine/scenario_runner.py:367`，缺 call 直接报错于 :387），无法轮询 DB；HTTP 层仅有 401 单次重取（`engine/http_client.py`），无通用重试。
- **业界做法**：Karate `retry until` 可挂在任意请求/断言上；Tavern 支持 stage 级 max_retries/delay。
- **建议草案**：扩展 `poll` 支持 `db_query` 轮询体（语法层复用现有信封，改动集中在 `step_poll`）；或更通用地给 verify 断言加 `retry: {times, interval_ms}`。前者改动小，推荐前者。

### P1-2 JSON Schema 断言

- **现状证据**：verify 断言家族为逐字段 `json{eq/ne/not_null/contains/len_gt/len_eq/absent}`（注册见 `engine/scenario_runner.py:672-678` 周边 verify 段），无结构/类型级整体校验。
- **业界做法**：Karate fuzzy match（`#string`/`#number`/`##optional`）、Tavern 响应 schema 块、Schemathesis 全量契约校验。
- **建议草案**：新增断言器类型 `schema`（走断言器注册，**语法层零变更**）：
  ```yaml
  verify:
    - schema:
        of: createResp
        spec:
          type: object
          required: [id, name]
          properties: {id: {type: integer}, name: {type: string}}
  ```
  依赖 `jsonschema` 库（新增依赖，需按 AGENTS.md §Ask First 评审）。`spec` 可支持 `file:` 引用外部 schema 文件，配合 P1-3 fixtures 预检。

### P1-3 fixtures 声明与加载期预检（承接 U-4，已拖欠）

- **现状证据**：场景引用本地文件（如 body `@test-data/x.xlsx`）只能运行期 SkipScenario；2.3.0 的 requires/T8 预检只覆盖账号/环境键/上游变量，不覆盖文件（`docs/引擎升级建议-DB断言与异步轮询.md` U-4）。
- **业界做法**：pytest fixtures、Karate `karate-config.js` 启动期解析。
- **建议草案**：场景头新增 `fixtures: [test-data/x.xlsx]`，加载期 T 级校验文件存在性，缺失 → 预检 FAIL（而非运行期 SKIP），workbench 编辑器同步提示。

### P2-1 数据驱动参数化

- **业界做法**：Karate Scenario Outline + Examples 表/CSV；HttpRunner parameters；Tavern parametrize marks。
- **建议草案**：场景级 `params:`（内联行表或 `csv: path`），加载期渲染为多实例，实例名 `场景ID#行号`；与现有 exclusive 多实例报告机制天然兼容。**动语法层，需冻结层评审**。

### P2-2 场景级超时

- **现状证据**：仅 HTTP 请求级 `timeout`（`engine/scenario_runner.py` call 段）与 poll 级 `timeout_ms`，无场景整体超时兜底；慢上游可拖死整轮回归。
- **建议草案**：场景元字段 `timeout_ms`，执行器计时超限 → verdict=FAIL、category=CAT_TIMEOUT（或按诚实语义归 CAT_ENV 时由 requires 判定）。

### P3 观察项（不排期，仅记录）

- **P3-1 并行执行**：pytest-xdist 或自建 worker；前置矛盾是 LeaseRegistry 租约与账号池为 session 内单例，并行需先解决资源竞争。
- **P3-2 tool 运行时热加载**：总表第 13 节差距矩阵已列（现为 Python import 静态注册）。
- **P3-3 python 步骤沙箱**：现为非沙箱 exec，多用户/远端触发场景下有安全面。
- **P3-4 契约 fuzzing**：Schemathesis 类工具基于 OpenAPI 自动生成边界用例。与 SpecGuard「Spec 锚点驱动」路线互补而非替代，建议作为**独立工具链**评估，不进引擎。

## 四、不建议做（与定位无关）

- **Mock server**：Karate 内置 mock 面向契约开发期，SpecGuard 打真实 SIT 环境，无此需求。
- **UI 自动化**：Karate/Playwright 领域，与后端场景引擎无关。
- **性能压测**：k6/JMeter 领域，引擎串行 session 模型本就不为此设计。
