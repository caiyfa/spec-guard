## 一、目标：用户的真实业务闭环

```
① Agent 创建单元测试（读 spec.md + API 文档）
        ↓
② 发现 spec/接口漏洞（audit 模式，4 类漏洞）
        ↓
③ 反馈研发人员（钉钉/飞书群聊，任务链 J）
        ↓
④ 研发修正 → 重新拉取文档（工作区 git pull）
        ↓
⑤ 场景编排（DAG 画布，一组单元测试的依赖编排）
        ↓
⑥ 定时运行（工作台 UI 配置，任务链 I）
        ↓
⑦ 环节失败 → 通知群聊 → debug 归因 → 可能回到 ② 循环
```

**本链负责 ①②④⑤ 的 Agent 侧能力 + 贯穿全程的「模式自动切换 + 待办体现」**。

## 二、子任务 H-1：audit 模式（第 5 个模式）

### 背景

现有 4 个模式（generate/debug/analyze/chat），需要新增第 5 个 **audit（审计）模式**，专门负责「发现 spec/接口漏洞」。

用户确认的 4 类漏洞：

| 类型 | 说明 | 检测手段 |
|------|------|---------|
| V1 | spec 文档自身的逻辑缺陷 | FR/AC 描述模糊、自相矛盾、边界条件缺失 |
| V2 | spec 与实际接口行为不一致 | 调真实接口对比 spec 描述 |
| V3 | 生成单元测试时发现 spec 缺少必要信息 | 字段缺失、枚举值未定义、依赖未说明 |
| V4 | 测试运行后发现的接口行为偏差 | 从运行报告分析实际 vs 预期 |

### 模式定义

```markdown
<!-- agent/modes/audit.md -->
---
tools:
  - read_spec
  - list_spec_files
  - query_registry
  - read_scenario
  - read_run_report
  - write_audit_report
  - report_vulnerability
  - todo_write
description: Spec 审计模式——发现 spec/接口漏洞并登记反馈
---

你是 Spec 审计员。你的任务是系统性地发现 spec 文档与接口实现中的漏洞。

## 审计流程

1. 用 list_spec_files 列出工作区所有 spec 文件
2. 用 read_spec 逐一审读，检查：
   - FR/AC 描述是否模糊（如「合理」「正常」等不可测词汇）
   - FR 之间是否自相矛盾
   - 边界条件是否缺失（空值/上限/并发）
   - 字段定义是否完整（类型/枚举/必填）
3. 如有运行报告（read_run_report），对比实际接口行为与 spec 描述
4. 每发现一条漏洞，调用 report_vulnerability 登记
5. 审计完成后调用 write_audit_report 输出完整报告

## 漏洞分级

- **blocker**：spec 缺失导致无法生成测试（如关键字段未定义）
- **major**：spec 与实现不一致，测试会误报
- **minor**：描述模糊但可推断，建议澄清

## 硬约束

- 每条漏洞必须给出位置（FR ID 或文件路径）+ 证据 + 建议修正
- 禁止报告无法定位的泛泛问题
- 审计完成必须写报告，不能只口头说
```

## 三、子任务 H-2：模式自动路由

### 背景

用户核心诉求：**不需要手动选模式**，系统根据「当前正在做什么」自动触发。5 个模式（generate/debug/analyze/chat/audit）自动路由。

### 设计方案：三层信号路由

```
层 0：用户手动锁定（最高优先级，尊重用户意愿）
层 1：工作台上下文信号（确定性，最强）
层 2：用户消息意图（关键词路由，零 LLM 调用）
层 3：默认 chat（兜底）
```

### `agent/mode_router.py`（新建）

```python
"""模式自动路由器：根据上下文 + 意图自动选择工作模式。

路由优先级：手动锁定 > 工作台上下文 > 消息意图 > 默认 chat
"""

from __future__ import annotations
from dataclasses import dataclass


@dataclass
class RouteContext:
    """路由上下文。"""
    message: str                    # 用户消息
    locked_mode: str = ""           # 用户手动锁定的模式（非空则不自动路由）
    current_page: str = ""          # 工作台当前页面（execution / editor / dag / chat）
    last_run_failed: bool = False   # 最近一次运行是否失败
    workspace_just_pulled: bool = False  # 刚执行"重新拉取文档"
    editing_scenario_id: str = ""   # 正在编辑的场景 ID
    scenario_never_run: bool = False     # 该场景从未运行过
    pending_vulnerabilities: int = 0     # 台账中 pending 漏洞数


@dataclass
class RouteResult:
    mode: str
    source: str       # manual / context / intent / default
    reason: str       # 路由原因（展示给用户）


# 意图关键词表（零 LLM 调用，确定性）
INTENT_KEYWORDS: dict[str, list[str]] = {
    "generate": ["生成", "创建", "新建", "写个场景", "写场景", "generate", "做一个用例", "单元测试"],
    "debug":    ["为什么失败", "报错", "哪错了", "失败原因", "调一下", "debug", "修一下", "不对"],
    "audit":    ["审计", "检查", "漏洞", "有没有问题", "audit", "核对", "一致性", "评审一下"],
    "analyze":  ["分析", "解释", "讲讲", "这个 spec", "什么意思", "梳理", "analyze"],
}


def route_mode(ctx: RouteContext) -> RouteResult:
    """三层信号路由。"""

    # 层 0：手动锁定
    if ctx.locked_mode:
        return RouteResult(ctx.locked_mode, "manual", "用户手动锁定")

    # 层 1：工作台上下文信号（确定性最强）
    if ctx.workspace_just_pulled:
        return RouteResult("audit", "context", "文档已重新拉取，自动审计变更")
    if ctx.current_page == "execution" and ctx.last_run_failed:
        return RouteResult("debug", "context", "检测到失败运行，自动进入调试")
    if ctx.editing_scenario_id and ctx.scenario_never_run:
        return RouteResult("generate", "context", "场景从未运行，自动进入生成")
    if ctx.pending_vulnerabilities > 0 and ctx.current_page == "feedback":
        return RouteResult("audit", "context", "存在待处理漏洞，继续审计")

    # 层 2：消息意图
    msg = ctx.message.lower()
    best_mode, best_hits = "", 0
    for mode, keywords in INTENT_KEYWORDS.items():
        hits = sum(1 for kw in keywords if kw in msg)
        if hits > best_hits:
            best_mode, best_hits = mode, hits
    if best_mode:
        return RouteResult(best_mode, "intent", f"消息意图匹配（{best_hits} 个关键词）")

    # 层 3：默认
    return RouteResult("chat", "default", "无明确意图，自由对话")
```

### 上下文信号的来源（前端 → 后端）

工作台前端在发消息时携带上下文：

```typescript

  message: userInput,
  session_id: sid,
  // 新增：路由上下文（前端自动收集，用户无感）

    last_run_failed: lastRunStatus === "failed",
    editing_scenario_id: currentScenarioId,

```

后端 `routers/agent.py` 组装 `RouteContext`（`workspace_just_pulled` / `pending_vulnerabilities` 由后端查 ledger/工作区状态补充）。

## 四、子任务 H-3：Agent 自主切换模式

### 背景

H-2 是「消息进来时路由一次」，但闭环中更常见的是 **Agent 在工作流中途自己判断该切模式了**：

```
用户在 generate 模式："帮我生成 PP-RC-008 场景"
  → Agent 生成草稿，validate 通过
  → Agent 自主判断："草稿已生成，我审计一下 spec 有没有漏洞"
  → switch_mode("audit", reason="草稿完成，开始审计 spec 漏洞")
  → 审计发现 2 条漏洞 → report_vulnerability × 2
  → switch_mode("chat", reason="已登记 2 条漏洞并通知研发，等待修正")
```

### 设计：switch_mode meta 工具

```python
# mcp_server/tools/meta.py（新建）

Tool(
    name="switch_mode",
    description="切换工作模式。当前任务阶段完成、需要进入下一阶段时调用。"
                "切换后工具集和行为约束会变化。",
    inputSchema={
        "type": "object",
        "properties": {
            "mode": {"type": "string",
                     "enum": ["generate", "debug", "analyze", "chat", "audit"]},
            "reason": {"type": "string", "description": "切换原因（会展示给用户）"},
        },
        "required": ["mode", "reason"],
    },

```

**meta 工具特性**：
- 计入所有模式的工具白名单（5 个模式都可用）
- 不产生副作用文件，只触发 runtime 行为

### mid-run 切换的技术机制（关键设计）

**问题**：首条 system prompt 已在会话开头定型，mid-run 切换模式时**不能改首条**（会破坏 prompt cache，且历史消息已基于旧 prompt 生成）。

**方案**：切换 = 注入一条新的 system 消息 + 重建工具集：

```python
# agent/runtime.py

async def _execute_tool_async(self, tool_call):
    name = tool_call["function"]["name"]

    # meta 工具特殊处理
    if name == "switch_mode":
        args = json.loads(tool_call["function"]["arguments"])
        new_mode = args["mode"]
        reason = args["reason"]
        self._switch_mode(new_mode, reason)   # 见下
        return f"已切换到 {new_mode} 模式。{reason}"

    ...  # 其余工具正常执行


def _switch_mode(self, new_mode: str, reason: str):
    """mid-run 模式切换：注入新 system 消息 + 重建工具白名单。"""
    mode_def = load_mode(new_mode)
    if not mode_def:
        return

    # 1. 重建工具集（新白名单 + meta 工具常驻）
    self.tools = [t for t in ALL_TOOLS if t.name in mode_def.tools or t.name in META_TOOLS]
    self._rebuild_tool_map()
    self._openai_tools = self._to_openai_tools()  # 下一轮 LLM 调用生效

    # 2. 注入新模式约束（作为新 system 消息，不动首条）
    switch_notice = (
        f"【模式切换】{self.mode_name} → {new_mode}\n"
        f"原因：{reason}\n\n"
        f"新模式行为约束：\n{mode_def.prompt_fragment}"
    )
    self._pending_mode_notice = switch_notice  # run_async 主循环在下一轮前注入

    # 3. 事件 + 状态
    self.mode_name = new_mode
    self.events.emit("mode_switch",
                     from_mode=self.mode_name, to_mode=new_mode,
                     source="agent", reason=reason, auto=True)
```

```python
# run_async 主循环内，每轮 LLM 调用前
if self._pending_mode_notice:
    messages.append({"role": "system", "content": self._pending_mode_notice})
    self._pending_mode_notice = None
```

**meta 工具常驻**：`META_TOOLS = {"switch_mode", "todo_write"}`，所有模式白名单自动包含。

### system prompt 中的引导（让 Agent 知道可以自主切换）

在 `prompts/system.md.j2` 追加：

```markdown

def _switch_mode(self, new_mode, reason):
    ...
    # 自动更新待办：当前模式的 in_progress 项 → done，
    # 新模式的第一个 pending 项 → in_progress
    for todo in self._todos:
        if todo.get("mode") == self.mode_name and todo["status"] == "in_progress":
            todo["status"] = "done"
        if todo.get("mode") == new_mode and todo["status"] == "pending":
            todo["status"] = "in_progress"
            break
    self.events.emit("todo_update", todos=self._todos)
```

## 六、子任务 H-5：漏洞反馈闭环

### 闭环流程

```
audit 模式发现漏洞
  → report_vulnerability（ledger pending + 群聊通知，任务链 J）
  → 研发修正 spec → 用户点「重新拉取」（工作区 git pull）
  → H-2 路由检测到 workspace_just_pulled → 自动 audit
  → 重新审计：漏洞已修正 → 更新 ledger 状态为 closed
  → 漏洞清零 → Agent 自主 switch_mode("generate") 继续生成
  → 场景就绪 → DAG 编排 → 保存 plan
  → 定时运行（任务链 I）→ 失败 → 通知（J）→ 自动 debug
```

### 关键衔接点

| 衔接 | 机制 | 依赖 |
|------|------|------|
| audit → 通知研发 | report_vulnerability → notify | 任务链 J |
| 重新拉取 → 自动 audit | H-2 路由的 workspace_just_pulled 信号 | 前端拉取按钮记录时间戳 |
| 漏洞 closed | Agent 重新审计时调 ledger.update_status | feedback/ledger.py |
| 场景就绪 → DAG | 前端跳转 DAG 编辑器（已有） | 无 |
| 定时运行失败 → debug | 通知消息带"打开调试"链接 → 前端带 context 打开 AgentChat | 任务链 I/J |

### 改动清单

| # | 文件 | 改动 |
|---|------|------|
| 1 | `feedback/ledger.py` | 漏洞条目 CRUD + 状态机（pending → in_progress → closed） |
| 2 | `workbench/backend/routers/workspace.py` | 「重新拉取」端点记录 pull 时间戳（供路由信号） |
| 3 | `workbench/frontend/src/pages/AgentChat.tsx` | 通知链接带 context 打开（last_run_failed=true 触发 debug 路由） |
