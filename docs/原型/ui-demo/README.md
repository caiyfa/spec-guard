## 各自的适合与代价

**A「Instrument 仪表」**——工程风险最低的主线候选。
方案文档 L0/L1/L2 结构（描边徽章、ghost 三档按钮、透明度三档、hairline）本质上就是 A 语言的条文，
T-1042 mermaid 描边徽章升级（e874d8c）是它在生产上的局部实证；现网默认 midnight 深色，用户零迁移成本。
代价：与现网差异最小=惊艳感最低，第一印象是「变精致了」而非「焕然一新」。

**B「Paper 纸面」**——阅读体验最好的差异化候选。
衬线 + 留白 + 墨色按钮与「契约/规范」产品调性契合，ScenarioReader/spec 文档等重度阅读场景最受益。
代价：① 现网五主题四深一浅、默认深色，默认浅色是全站第一印象的翻转；② Monaco/React Flow/mermaid
均为深色原生组件，纸上需要逐个「裱框」；③ 微阴影在 frost 磨砂下被玻璃模糊吃掉；④ 落地调校成本最高。

**C「Terminal 终端」**——性格最强的极客候选。
与「契约驱动测试引擎」的工程师气质绝配；字符徽章/反白选中零渲染负担、对比度天然最高；
全等宽让 E10（emoji 宽度对齐）问题彻底消失。
代价：① 全 mono 中文长文阅读（spec/消息流）疲劳度高；② 荧光色的浅色版（打印纸）需要全量重校；
③ 非工程背景用户可能被劝退；④ 与 frost 玻璃拟态、K-044 背景图玩法冲突明显。

## 推荐意见：**A 为主线定稿，吸收 B 的阅读层养分，C 捐赠创意**

**推荐 A**，五条理由：

1. **工程风险最低**——U0~U4 分期（方案 §六）几乎是「按 demo 抄」：L0 tokens（字号阶梯/透明度档次/
   逃逸色映射）与 L1 六原语（StatusBadge/Button 三档/Tabs/StateView/Toast/Modal）在 A demo 里已全部
   成形且深浅两版验证过；选 B/C 都要在方案结构之外再发明一批组件形态并承担相应返工。
2. **用户迁移成本最低**——现网默认 midnight 深色、五主题四深一浅；A 深色优先顺其自然，
   B 默认浅色是 100% 的第一印象翻转（风险表 §八「用户已习惯现有密度/风格」条目的最大触发器）。
3. **深色原生组件零适配**——Monaco/React Flow/mermaid/elkjs 画布都是深色原生，A 无缝承接；
   B 的纸面需要为每个深色组件单独设计「裱框」，C 的辉光在 frost 下与玻璃模糊打架。
4. **已被生产验证过一次**——T-1042 mermaid 描边徽章（e874d8c，总控人目检通过）本质就是 A 语言的
   局部胜利；选 A 是把已验证的赌注放大，不是开新赌局。
5. **B/C 的养分可以吸收而非二选一**——阅读场景（ScenarioReader/spec 完整文档弹层/场景编辑器）
   可引入 B 的衬线标题 + 大留白作为 A 的「阅读模式」子语言；C 的 `[OK]/[FAIL]` 日志行 Toast、
   `[████░░]` 进度条骨架可捐赠给 A 的执行日志/试跑面板区域（这两处本来就是日志语义）。

**不推荐全站 C 化**，但 C 可作为远期「彩蛋主题」登记（主题多维化后：色板+圆角+密度+描边+字体打包，
终端包是现成的第六主题候选），其字符徽章语法与 A 的描边徽章兼容（同为描边系）。

## flow 图渲染器裁决建议（阶段二输入）

三套 demo 的 flow 图均为**手绘 SVG**，原因一致：mermaid `classDef` 只支持 fill/stroke，
表达不了 A 的「当前外环辉光」、B 的「卡片纸影 + 左状态条」、C 的「方角 + 辉光」。
建议按定稿方向分流：

- **定稿 A**（推荐路径）：flow 图升级为**专用 SVG 渲染器**——`evals/flows/*.flow.json` 已是
  结构化单一事实源（12 阶段/21 边/门/约束/热力齐全），写一个 ~300 行的确定性布局+渲染函数
  （demo 已给出布局坐标与视觉规范），替换 `render_flow_mermaid`；mermaid 留作报告导出降级。
- 若想控制工程量：A 的节点也可降级为「mermaid 描边徽章 + current 提权描边」（现网已实现），
  辉光/角标放弃——**demo 与现网的差距就是这一刀，裁决点在这里**。
- 定稿 B/C：同理需要专用渲染器（B 的阴影、C 的辉光均超出 mermaid 能力）。
