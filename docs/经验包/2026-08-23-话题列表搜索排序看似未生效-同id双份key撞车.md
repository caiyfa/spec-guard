# 2026-08-23 话题列表搜索/排序看似未生效——candidates/confirmed 同 id 双份 + React key 撞车

## 现象

总控人 08-23 在话题工作台（T-1001 当日验收合并后）实测：搜索框输入「BUG」、排序选「消息数 多→少」，
列表内容看似毫无变化——计数从「18 项」变为「4 项」，但可视卡片仍是未过滤、未重排的那批。
无任务号（UI 交互缺陷，非执行运行）。

## 证据链

- 页面快照（vite dev :5173，当前 master 代码 fresh load）：右栏 9 个话题每个渲染**两次**（
  「报告断档邮箱问题分析」×2、「客观标签生产全量重跑」×2…），状态页签显示「全部 18」；
  稳定渲染序 = 同 ts 并列对（`[...candidates, ...confirmed]` 稳定排序的可判定特征序）。
- 输入「BUG」稳定态：计数「4 项」（= 2 个命中话题 × 2 份），列表却渲染 13 张卡
  （7 非命中 ×1 + 2 命中 ×3）——计数与列表 DOM 脱节，React 协调撕裂的典型形态。
- 真实数据复演（`specguard-space/.specflow/90024166/feishu_pool/_topics.yaml`）：
  该群仅 9 话题（全 confirmed），「bug」命中应恰为 2 个标题；排除「摘要截断藏命中词」的可能。
- 数据源代码：`feishu_sync_service.py:798 list_pool_topics`——
  `candidates = tc._load_candidates(私有区 _topics.yaml)`（含 status=confirmed 卡）
  `confirmed = facts.load_topics(共享区 facts 事实源)`（确认时 `_set_status` 提升写入）；
  两列表包含同一批已确认话题（docstring 自述「T-949 合并为单一存储后此区分退役」但响应未收敛）。
- 渲染代码：`TopicWorkspace.tsx` 列表 `key={t.id}`；对照 `FeishuPool.tsx` 页头 allTopicCards
  早有 byId 去重（所以页签徽标 23 一直是对的）——工作台拼接处漏了同一步。

## 根因

数据层：已确认话题**双存**（私有区 _topics.yaml 状态制卡 + 共享区 facts 事实源），接口
`candidates`/`confirmed` 两数组同 id 各带一份 → 前端拼接出 18 条同 key 记录。
渲染层：React 兄弟节点 key 重复（9 个 id × 2）→ 协调结果不可预期——计数走新数据（4），
列表 DOM 滞留旧树（13/18 混杂），搜索/排序因此「看似未生效」。
（环节：实现层——T-949 双存储设计留下的接口重叠，经 T-1001 列表化暴露为可视缺陷。）

## 修复

（提交号见本节落盘后回填）前端防御性去重，不动后端响应形状（页头「候选话题/已确认话题」
计数仍消费原两数组）：

- `topicList.ts` 新增 `dedupeTopics`（Map 语义：同 id 后值覆盖先值、位置保持首次——与页头
  byId 完全同口径；调用按 `[...confirmed, ...candidates]` 传入即 _topics.yaml 副本胜出）；
- `TopicWorkspace.dayTopics` 先 `dedupeTopics([...confirmed, ...candidates])` 再过滤 →
  key 唯一，渲染与数据重新一致，搜索/排序即刻生效；
- `FeishuPool.allTopicCards` 内联 byId 去重收敛为同一 `dedupeTopics`（行为零漂移）；
- 同提交落地总控人新需求「标签筛选」：`collectKeywords` 词频芯片行 + `filterTopics`
  `tags` 参（多选 AND），芯片计数为分面口径（其他筛选已生效、标签未生效），选择持久化；
- 单测：dedupeTopics 3 例 + collectKeywords 2 例 + tags 4 例（vitest 83→92）。

## 预防

- 凡「接口返回多个数组由前端拼接」的页面，拼接后**必须过 id 去重**再进渲染列表；
  key 用业务 id 时先确认 id 在该列表内唯一（React duplicate key 不报错只警告，且撕裂形态
  在 mount/update 路径不同——「计数变了列表没变」是第一信号）。
- 计数/徽标与列表渲染必须消费**同一份**派生数组（本次计数用过滤后、列表渲染滞留旧树，
  两者数据源一致本可更早暴露）。
- 后端清理项（另立任务，不随本次）：`list_pool_topics` 的 `confirmed` 数组是 T-949
  单一存储后的遗留重叠，待页头计数改造后可退役（响应收敛 candidates-only）。
- 排查「控件看似不生效」类问题先查 React DevTools key 警告/列表项数与数据项数是否一致。
