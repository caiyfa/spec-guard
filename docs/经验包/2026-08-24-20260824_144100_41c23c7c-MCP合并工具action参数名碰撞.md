# MCP 合并工具 action 参数名碰撞（spec sync 不可用）

## 现象

- **会话**：20260824_144100_41c23c7c（人才发展工作区，用户指令「拉取最新spec文档」）
- **报错**：`spec(action=sync)` 连续 3 次返回 `错误：未知 action: （合法值: sync / dismiss）`——action 值显示为**空**，但合法值提示本身含 sync
- **对照**：同会话 `spec(action=list, subdir=changes)` 正常返回——工具调用链本身无异常
- Agent 按 K-020 停止操作并如实上报（行为正确），用户侧表现为「拉取最新 spec 文档」完全不可用

## 证据链

1. 会话消息链（`agent/sessions/90024166/人才发展/20260824_144100_41c23c7c.jsonl` 第 4-11 行）：
   3 次 `spec(action=sync)` 同错、1 次 `spec(action=list)` 正常
2. 合并层代码（`mcp_server/tools/tool_meta.py` consolidate handle）：
   `action = str(args.pop("action", "") or "")` 把合并层 action **弹出并消费**后委派 legacy handler，
   剩余参数里不再有 action 键
3. legacy 工具（`mcp_server/tools/spec_reader.py` _handle_sync_workspace）：
   `action = arguments.get("action", "")`——**自己的必填参数恰好也叫 action**（enum: sync/dismiss），
   拿到空值落入兜底分支报错
4. 本地复现（修复前）：`spec(action=sync)` → `错误：未知 action: （合法值: sync / dismiss）`，
   与会话实录逐字一致；`scenario(action=edit, scenario_id=…, dep_id=…)` →
   `错误：action 非法: （仅支持 add/remove）`（同根因潜伏，DAG 编排加删边同样不可用）

## 根因

T-982 工具合并（77 碎片 → 24 合并工具）时**参数名冲突未检查**：合并层用 `action` 承载子命令，
而 legacy 工具 `sync_workspace` / `edit_dependency` 自带的业务参数恰好也叫 `action`——

- 运行时：合并层 pop 掉 action 后委派，legacy handler 拿到空 action；
- schema 层：属性并集 `if pn not in props` 同名属性丢弃，合并 schema 里 edit_dependency 的
  add/remove 枚举被外层 action 挤掉，**LLM 在合并面上根本无法表达加边/删边**；
- 附带损失：`dismiss`（会话级不再提醒）在合并面只暴露了 sync 单 action，能力收敛中丢失。

为什么测试没拦住：test_mcp_server.py 存量用例全走 legacy 兼容通道（直接用旧工具名调用），
合并面（合并工具名 + action 参数）对这两个工具零覆盖。

## 修复

- `tool_meta.py`：`ActionMeta` 新增 `params` 字段——consolidate 委派时按声明注入固定参数
  （用户显式传参优先，setdefault），通用机制 ~10 行
- `spec_reader.py`：合并 action 拆为 `sync` + `dismiss`（各配 `params={"action": …}` 注入 legacy），
  dismiss 能力在合并面找回；`_read_with_remote_status` 决策提示文案同步改为 `spec(action=…)`
- `scenario_tools.py`：`edit_dependency` 内层参数 `action` → `op`（add/remove 是运行时选择，
  无法用固定 params 表达）；handler 双读兼容（`op` 优先、legacy 通道 `action` 仍接受，
  REST /deps 端点独立实现不受影响）
- `agent/skills/dag-orchestration.md`：落地单条边调用姿势改为
  `scenario(action=edit, op=add/remove, …)`（原文案一次调用传两个 action 键，JSON 层面不可能成立）
- 回归测试 ×6（test_mcp_server.py 合并面覆盖，TDD 先红后绿）：spec sync/dismiss 到达分支、
  双 action 枚举、scenario edit 的 op 表达与 schema 暴露、legacy 通道兼容
- 顺手修复（Boy Scout）：spec_reader F401（SIDE_DRAFT 未使用）+ F841×2（BACKEND_DIR）+ I001，
  tool_meta B007 + I001
- 验证：test_mcp_server 66 绿；联动 test_delta_committer/test_delta_doc_writer/
  test_skill_governance/test_topic_digest 共 167 绿；ruff 目标文件清零；ALL_TOOLS=40 不变

## 预防

1. **新增合并工具 action 时检查参数名冲突**：legacy 工具 inputSchema 的 properties/required
   里若含 `action`，必须二选一——固定语义可 `ActionMeta(params={...})` 注入拆 action；
   运行时多值语义必须改 legacy 参数名（不得与合并层 action 同名）
2. **合并面必须有测试**：legacy 通道测试不等于合并面测试——每个合并工具至少 1 条用例
   走「合并工具名 + action 参数」路径（本次 6 条缺口即由此漏过）
3. **skills/文档中的工具调用姿势要可执行**：一次调用同一参数键只能出现一次；
   引用合并工具参数签名时与 inputSchema 实际属性核对
4. 工具收敛/重构类任务收尾时，对全部 legacy 工具 schema 做一次同名参数扫描
   （`rg '"action"' mcp_server/tools/` 逐个比对 consolidate actions 声明）
