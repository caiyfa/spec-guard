# 语义召回候选层 — 需求面试自然语言理解的检索增强构想

> **状态：暂缓（甜点类需求）**。2026-08-26 由「SpecGuard 检索/工具/记忆三维度能力分析」讨论收敛而来：确定性检索体系在测试侧是护栏性设计（可审计、可复现、零 LLM 路由），不应替换；但需求侧面试闭环存在「理解产品自然语言表述」的真实缺口。本文沉淀设计共识与重启条件，将来重启时按此施工，不重新讨论。

---

## 一、背景与触发场景

SpecGuard 的检索/记忆体系贯彻「零向量、零语义检索、零 LLM 路由」：文本检索是带标识符边界的子串/正则（`spec_search`），关联查找靠图谱确定性遍历（covers/depends_on/backlink/lineage），知识触发靠关键词与错误签名（`knowledge_index` 双通道）。这套确定性在测试侧是正确取舍——血缘链「这个场景为什么存在」要求逐字节可复现，审计证据不能依赖 embedding 漂移。

但**需求侧 specflow 面试闭环**的场景不同：产品经理用自然语言描述需求（"干部要能看下属的历史评价情况"），Agent 需要将其映射到候选 FR/AC/既有场景。当前的承接方式是**流程消化**——面试闭环人工对齐 + 话题聚类议题卡 + 未闭环 SPQ 信息包装配，把模糊性消化在多轮对话里，而非检索里。缺口显性化的形态：

- 产品用户换一种说法描述既有需求，子串/关键词检索找不到（「绩效」≠「评价」≠「考核」）；
- 新人 onboarding 用模糊语言找资料，图谱三职责镜头（面试选题/测试债地图/onboarding）只覆盖固定导航路径，不响应自由查询；
- 场景/spec 规模膨胀后，`network_view` 500 节点护栏降级为聚合态，人工导航邻域变难。

## 二、需求本质（一句话）

**确定性检索回答「ID 是什么」，语义召回回答「像什么」**——在 FR 锚点纪律与候选发现之间加一层显式的、可否决的语义匹配，让产品的模糊表述能触达候选契约，但结论仍锚定在确定性 ID 上。

## 三、结论：为何暂缓

- 面试闭环的模糊性当前由流程消化（人工对齐 + 议题卡 + 信息包），痛点未显性化为瓶颈；
- 内网 embedding 基础设施未就绪（自建有运维成本、外呼有数据出域风险），零向量=零依赖仍是当前最优；
- 当前规模（原型基准 ~298 FR / 25 场景）下图谱邻域 + 三职责镜头可人工导航，500 节点护栏未频繁触发；
- 语义层一旦引入，须防止污染确定性红线——设计成本高，值得等真实信号再付。

## 四、设计要点（重启时的施工蓝图）

### 4.1 核心决策：语义召回只做候选标注，不做检索通道替换

**召回结果落为显式的候选边/候选锚点（proposal），由人或确定性校验确认后才入图**——与「LLM 生成草稿、三道闸把关」完全同构。语义相似度永远不直接成为依据：检索可以辅助**发现**，结论必须**锚定**（FR-xxx 注册表锚定解析仍是最终权威）。

不做的形态（明确排除）：

- 不把向量检索做成 `spec_search` 的替代或默认通道；
- 不让语义匹配结果直接注入 lineage/backlink 查询结果（审计证据链保持确定性）；
- 不做 LLM 路由的知识注入（`knowledge_index` 现有红线「不做 agent 输出匹配防回环」继续有效）。

### 4.2 四层结构

| 层 | 职责 | 形态 |
|---|---|---|
| 召回层 | embedding 索引：FR/AC/场景标题+摘要/glossary 词条向量化 | 派生物（同 `graph_index.db` 模式：指纹失效重建、可删可重建、绝不回写源数据） |
| 候选层 | 语义匹配产出 proposal：`{query, candidate_id, score, status: proposed}` | 显式落盘（如 `.specguard/proposals/`），带置信度，**不进图谱正式边** |
| 确认层 | 双闸：人（面试会话中产品用户点确认）或确定性校验（`parse_fr_id` 锚点合法性 + 功能注册表匹配） | proposal → confirmed / rejected，rejected 留痕反哺召回阈值调优 |
| 入图层 | confirmed proposal 转为正式类型化边（如面试议题 `mentions` FR） | 从此走确定性遍历，语义层功成身退 |

### 4.3 首个落地场景（不要贪多）

面试会话「影响面确认」环节：Agent 基于议题卡文本做语义召回 → 候选 FR 集以 proposal 呈现给产品用户 → 确认后挂 `mentions` 边进图谱 → G2 影响面图谱视图直接消费。这条链路复用现有 specflow F1 决策台账 + 图谱边机制，语义层只在最前端出现一次。

### 4.4 三条红线

1. **派生物纪律**：向量索引与图谱同等待遇——源数据（spec/glossary/场景）指纹失效即重建，索引不落 git；
2. **确认前不上依据链**：proposal 不出现在 lineage_trace / backlink 结果中，doc_read 足迹不记录语义命中（阅读足迹只记确定性读取）；
3. **不出域**：embedding 服务必须内网可达（自建轻量模型或集团基础设施），否则整个构想不成立——数据出域换检索体验不符合企业落地前提。

### 4.5 与既有机制的分工

| 既有机制 | 分工 |
|---|---|
| `spec_search`（子串/正则） | ID 与精确文本定位的唯一通道，语义层不碰 |
| `graph_index`（确定性遍历） | 确认后的关联查询；proposal 确认即转入此层 |
| `knowledge_index`（关键词/签名触发） | 知识投递保持确定性，语义召回不进 nudge 通道 |
| 面试闭环人工对齐 | 确认层的人闸即嵌入此流程，不另建 UI |

## 五、重启条件（命中任一即升级）

1. 面试会话中「自然语言表述 → 候选 FR」的人工对齐成为**高频瓶颈**（如面试官/产品用户反复反馈"找不到相关 FR"、单次面试对齐轮次显著拉长）；
2. `graph network_view` 500 节点护栏**频繁触发**（truncated=true 成常态），或 FR 规模超 ~500 条，邻域无法人工导航；
3. 内网可用 embedding 基础设施就绪（自建或集团提供，数据不出域前提满足）；
4. 出现第 2 个语义匹配刚需场景（如新人 onboarding 自由查询、覆盖缺口热点模糊定位），共同形状可提炼。
