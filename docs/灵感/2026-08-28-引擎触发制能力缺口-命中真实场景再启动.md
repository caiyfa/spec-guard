# 引擎触发制能力缺口——命中真实场景再启动

> 日期：2026-08-28
> 来源：全方位测试强化调研（引擎能力边界扫描，17 项缺口核对）

## 背景与触发场景

2026-08-28 测试强化调研把引擎能力缺口逐项核对了一遍（`engine/` 实现 vs 两批升级建议 vs V3 待实施设计 vs 远期总控储备），共 17 项。其中 3 项有真实业务驱动已转入正式规划（`docs/远期设计/SpecGuard-测试体系强化-五方向调研与规划.md` §4：U-5 文件断言、T-503 DB 轮询、受限账号配置）。**其余 14 项全部是触发制储备**——想清楚了、有设计归属，但现在做是过度建设。本条灵感把它们收敛成一张清单，配上各自的可判定重启条件，避免未来每来一个同域需求就重新推导一遍"要不要做"。

## 需求本质（一句话抽象）

引擎能力的扩张一律应由**真实场景的第一处撞墙**驱动，而不是由"能力清单不完整"驱动——SpecGuard 引擎主线（契约驱动 DAG + 诚实语义 + DB/权限预言）已完整且多处超越开源对标（第三批总结论），剩余缺口都是边角与规模化问题。

## 结论（为何暂缓）

- 缺口分三类：①有明确触发条件的储备（总控已登记 T-503/T-504，V3 设计已就位）；②官方明示的能力边界（长期不做）；③断言表达力边角（有 python 逃生舱，ROI 不足）。
- 每类都有既存事实源，本清单只做**索引与重启条件**，不复制设计内容（防事实源分裂）。

## 设计要点（缺口清单 + 事实源指引）

### A. 储备类（触发制，事实源已存在）

| # | 缺口 | 事实源（重启时先读） | 重启条件 |
|---|------|---------------------|----------|
| 1 | DB 轮询（poll 仅 HTTP 体） | 总控 T-503；第三批 P1-1 | 首个"状态只在库里、无 HTTP 状态接口"的真实异步场景出现 |
| 2 | verify 级通用重试（瞬时 5xx 重断言） | 总控 T-503（同块） | 环境抖动假失败在 failures/index.jsonl 中成模式（同场景 ≥3 次间歇失败） |
| 3 | 数据驱动参数化（Scenario Outline/CSV） | 总控 T-504；动语法层需冻结层评审 | 异常/边界场景族铺开后出现"整份复制 YAML 只改数据"≥5 份（方向二落地时是首个观察点） |
| 4 | 场景级 YAML `timeout_ms` 字段 | 总控 T-504（同块）；现 SG_SCENARIO_TIMEOUT 全局软看门狗兜底 | 出现单场景需要区别于全局 300s 超时的真实归因需求 |
| 5 | DAG 分层并行执行 | V3 设计 §7.2；总控 T-802（执行槽池化） | 场景库回归耗时成为实际瓶颈（如全量 >30min）且串行优化到头 |
| 6 | produces/consumes 状态接力调度 | V3 设计 §六 | 写型场景 ≥10 个，且"同一资源多状态"导致上游重复重跑肉眼可见 |
| 7 | 环境配置层借用-归还租约 | V3 设计 §4.2 第四层/§六 | 配置类写场景互相踩踏出真实事故，或为并行硬互斥点 |
| 8 | 租约尽早回收（teardown 成功即 release） | V3 设计 §4.3；scenario_runner.py:1199 现仅 session 末 release_all | session 后段场景因租不到候选工号而 SKIP 成为常态（failures 台账 pool_leased_out 类 SKIP 增多） |

## 重启条件（本条灵感整体的升级信号）

- 清单中任一项的**单项重启条件命中** → 该项升级：A 类直接认领总控对应任务（T-503/T-504/T-802/V3 条款）或新建任务；B/C 类先过冻结层评审与总控人拍板。
- 方向二（负向/异常场景族）与方向一（浅断言深化）落地过程中会自然撞到 3、4、13、14 号——那两个方向开工时应先扫一遍本清单。
- 全部命中或清单过时（如引擎 3.0 立项）→ 本条灵感整体迁移/归档。
