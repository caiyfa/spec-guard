# 事实包 FactPack — 对话内事实消费与用户自助扩展构想

> **状态：暂缓（甜点类需求）**。2026-08-24 由「资源码映射工具集成」讨论收敛而来，判定当前不值得做；本文沉淀设计共识与重启条件，将来重启时按此施工，不重新讨论。

---

## 一、背景与触发场景

数据权限类测试用例生成需要「资源 code ↔ 后端接口路径 ↔ 菜单路径」的确定性对应关系，而资源 code 写死在前端代码里，测试人员读不懂前端代码。已有外部脚本（首个落地：`ifelc-ms-tdm-api/scripts/gen_resource_code_map.py`，扫描前端仓库 + 连 hr-center 库合并菜单路径，使用指南见同目录《前端资源code映射工具使用指南.md》）能产出 4 列 CSV：

```csv
resource_code,http_method,api_url,menu_path
VIEW_EVAL360,POST,/hr-tdm/api/eval/360/query,根目录/…/360评价/查看
```

问题抽象后不止这一个场景：凡是「外部代码库/数据库静态扫描 → 确定性事实产物 → agent 对话消费」的需求（候选：DB 字典/表结构导出、后端 Controller 路由↔权限注解扫描、hr-center 菜单树快照、枚举/状态机字典）都属于同一类。

## 二、需求本质（一句话）

**对话里上传了一个文件，agent 读取文件内容做后续操作**——即工作区级的事实性知识包（FactPack），区别于 skills（程序性知识：怎么做）与 info_pack（场景级需求材料）。

## 三、结论：为何暂缓

- 当前唯一消费者是资源码映射，且外部脚本 + 手工放置 CSV 已可用（低频够用）；
- 为单例建通用机制是过早抽象（rule of three 未满足）;
- 不影响现有任何流程——真需求出现时随时可捡起。

## 四、设计要点（重启时的施工蓝图）

### 4.1 核心决策：数据契约型，不是代码插件型

扩展点给**数据**（谁都能产），不给**代码**（评审才能进）。理由：

1. agent 消费的是事实数据而非脚本本身——冻结数据 schema 的兼容成本远低于冻结插件 API；
2. 与仓库信任模型一致：「可信靠评审」（ENG-SEC-001 场景 python 步骤 / steps.py 均 git 评审后入库）。用户脚本留在 SpecGuard 进程之外自己跑，只把**产物**按契约放进工作区——自助扩展与评审边界两头都保住；
3. 经典插件框架会让插件 API 即刻变成新冻结层，且自动加载执行用户 .py 要么绕过评审要么每次仍要评审。

### 4.2 三层结构

| 层 | 职责 | 谁维护 |
|---|---|---|
| 契约层 | kind 注册表 + manifest/行 schema 确定性校验器（specstd 风格，纯读） | 开发 |
| 消费层 | 单个通用 MCP 工具 `fact(action=list/query)`：list 返回各包新鲜度与校验状态；query 按字段反查 | 开发（一次） |
| 生成层 | 用户扫描脚本，进程外自管，产物落盘 | 用户自助 |

目录约定草案：

```
{ws}/.specguard/facts/
└── resource-code-map/
    ├── manifest.yaml    # schema_version / kind / description / generated_at /
    │                    # source(repo+commit) / confidence 语义 / 行数
    └── data.jsonl       # 事实行（含 confidence 列）
```

新事实源对 agent 可见性是数据驱动的——用户放好包，`fact(list)` 即发现，全程不改 mcp_server。

### 4.3 与既有机制的分工（避免重复建设）

| 既有机制 | 定位 | 分工 |
|---|---|---|
| `kg://{ws}/{layer}/{token}` | 工作区知识层读取 | facts 可作为新 layer 复用解析路径 |
| `info_pack`（G2-1） | **场景级**需求材料包（挂 scenario_id） | FactPack 是**工作区级**横向知识，粒度不同不合并 |
| `agent/skills/*.md` | 程序性知识，热加载可自写 | 对称物：技能教 agent 何时查、怎么解读置信度 |
| `integrations/` / 外部 MCP | 实时查询型集成 | 批量静态事实走 FactPack，实时拉取才走这条 |

### 4.4 三条红线

1. **提示注入防线**：事实数据只作 tool result 进对话（临时上下文），绝不注入 system prompt——注入面保留给评审过的 skills；
2. **诚实呈现劣化**：manifest 缺失 / 校验不过 / 超时效阈值的包如实标 stale·invalid，query 拒答或降级提示，不静默喂垃圾数据（SKIP 语义在知识层的延伸）;
3. **置信度进产物**：扫描置信度（如 exact/method/file 三级）保留为列，file 级启发式关联返回时标注待复核，指向运行时 `precheck_permission` / `fetch_permission` 兜底——静态映射给候选，动态预检给真相。

### 4.5 落地节奏

第一个包（资源码映射）直接按上述形状手工落地验证 → 攒到第 2~3 个同类场景 → 提炼正式契约（schema 校验器进 specstd + 通用 fact 工具一个任务块）→ 仅当刷新自动化成为真实痛点时才加受信生成器 runner（届时即 steps.py 模式，子进程隔离，生成器必须在 git 评审范围内）。

## 五、重启条件（命中任一即升级）

1. 数据权限类用例生成**高频**依赖资源码映射，人肉刷新 CSV 成为瓶颈；
2. 出现第 2~3 个真实的「外部扫描→事实→agent 消费」场景（DB 字典导出 / Controller 扫描 / 菜单树快照等），共同形状可提炼；
3. 接入第二个 FEMSP 体系被测系统，映射工具需多系统复用。
