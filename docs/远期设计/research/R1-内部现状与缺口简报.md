## 3. 缺口分析

**离「成体系的 skill 管理」还差**：
1. **注册表**：skills 只是目录扫描，无 `GET /api/agent/profiles` 式的查询面（M12 已为 profile 建了 API，skill 层没有）；
2. **版本/依赖**：frontmatter 无 version/depends 字段，skill 升级无变更留痕、无与 MCP 工具版本的兼容声明；
3. **权限**：frontmatter 声明 tools 但 `runtime.py` 分发前**不过滤**——M12 的三层交集白名单（TOOL_REGISTRY ∩ profile.tools ∩ rbac_visible_tools）是新建项；
4. **评估**：无 skill 质量评估/回归口径（仅有「热加载 30s 内可见」「越权被拒」这类机制级验收，无产出质量基准）；
5. **审查门禁**：新增 skill/profile 目前是「文件落盘即生效」，M12 验收红线（不改 runtime、不重启、绕闸=阻断缺陷）是纪律，尚无入库评审通道；
6. **分发/导入**：无跨仓库/跨工作区分发机制（现状=git 跟代码走，够用但无独立分发故事）。

**离「成体系的 MCP 体系」还差**：
1. **单 server 单 TOOL_MODULES**：无多 server 编排、无外部/远程 MCP server 接入客户端（zentao 走的是 zentao-cli 子进程，**绕开了** MCP——是有意的边界控制而非能力）；
2. **工具分类治理**：纯读/写两分的纪律靠 docstring 自觉，无元数据化分类注册（无 `side_effect: none|draft|external-write` 声明式字段与运行时校验）；
3. **副作用分级**：写类工具（draft_writer/audit）与触外部系统的写（zentao）无统一分级口径；M06 的「外部写不进 MCP」是个案决策，未成通则；
4. **审计**：无统一的 MCP 工具调用审计日志（谁、哪个会话、哪个工具、写了什么）——audit 模块是业务工具不是平台审计；
5. **欠账**：info_pack.py 未挂载是「实现了但没进体系」的典型样本。

## 4. 关键约束：8 条铁律对 skill/MCP 体系的硬要求

1. **铁律 1（Agent 只建议，人拍板）**：profile 必须有 `gate` 声明；Agent 产出只落草稿/建议区（suggestion 永不自动转 decided）；触外部系统的写不暴露给 MCP；
2. **铁律 2（校验走确定性校验器）**：校验/查询类 MCP 工具**纯读零副作用**；工具白名单过滤是确定性机制，不靠提示词自觉；
3. **铁律 3（每个产出必过闸）**：每个 Agent 卡片闸门逐实例化（三闸/P0 清零/数据校验器/人定性/产品确认回写），绕闸生效=阻断性缺陷；
4. **铁律 4（链可跨界，资产不跨界）**：平台不提供研发资产写接口；external_refs 只登记引用；回滚只回滚 SpecGuard 侧登记；
5. **铁律 5（被测系统解耦）**：新系统=新增适配包子包 + live_registry 导入注册，Agent/引擎零改动；
6. **铁律 6（计划只能由 delta 导入生成）**：数据制造 Agent 产物走同一草稿通道与三闸，不开旁路；
7. **铁律 7（诚实结果语义）**：归因 Agent 提示词+校验双侧固化，环境问题误报 FAIL 须复核改写 SKIP；
8. **铁律 8（不做编码智能体）**：profile 注册表评审项——任何新 Agent 白名单不得含代码生成/研发管理类工具。

## 5. 初步判断

**渐进式体系化是正确剂量**：运行时强制点（白名单三层交集、闸门声明、purpose 锁定、MCP 四步挂载规范）属**必须有**；而 skill 版本库、多 MCP server、独立分发市场、质量评估平台在当前规模（3 skill / 24 工具 / 5 Agent）属过度工程，等 Agent/工具数量翻倍再补不迟。
