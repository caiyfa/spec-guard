# SpecGuard 各场景 MCP 对外开放价值评估（含需求面试专题）

> 架构决策分析第三篇 · 2026-07
> 前提修正：现有 `mcp_server`（stdio、24 工具）是**测试侧早期产物**——工具面全部围绕场景库/草稿/执行，不含 specflow 需求侧、血缘、图谱任何能力，与远期规划已不适配。
> 问题：远期形态下，**各个场景**是否值得对外提供 MCP 服务？需求面试部分单独深评。

---

## 1. 结论摘要

**逐场景评估的总答案：值得开放的不到一半，且几乎全是「产物只读面」；最有价值的不是把现有工具搬出去，而是把远期规划里还没有的「spec 产物查询面」建成对外 MCP 的主体。**

| 判断 | 场景 |
|---|---|
| 🟢 值得开放（L0 只读，G2 落地） | 冻结 spec/锚点查询、覆盖缺口与测试债、执行报告、血缘链 trace、图谱索引、禅道反查、需求面试**产物**（spec/proposal/台账/评分/进度） |
| 🟡 受限开放（L1 草稿态，G3 评估） | 场景执行（run_scenario 子集）、归因建议提交、**面试议题提交** |
| 🔴 不值得开放 | **需求面试过程（对话与提问生成）**、材料包上传解析、决策落锤与五维确认、草稿晋升、测试数据制造、禅道写、图谱索引构建、平台管理 |

**需求面试专题一句话**：面试的**过程**是人机多轮对话 + 人拍板闸门，与 MCP「单次工具调用」的形态天然不匹配，**不应 MCP 化**；面试的**产物**（冻结 spec、决策台账、评分、进度状态）恰是外部最想要的东西，**应按 L0 只读开放**；面试的**入口**（议题提交）可按 L1 草稿态开放。即「过程不开放、产物全开放、入口半开放」。

---

## 2. 判断框架

### 2.1 消费模式四分（比「读/写」更细的尺度）

对外 MCP 的诉求可分成四种消费模式，适配度天然不同：

| 模式 | 说明 | MCP 适配度 |
|---|---|---|
| ① 读产物 | 查询已冻结/已归档的事实（spec、台账、报告、图谱） | ★★★ 天然匹配：单次调用、无状态、可缓存、可分级 |
| ② 触发流程 | 提交一个待办让平台内部流程接住（议题、草稿、归因建议） | ★★ 可匹配：草稿态写入 + 人接手，闸门不被稀释 |
| ③ 参与过程 | 外部 Agent 进入多轮协作（面试问答、评审讨论） | ★ 不匹配：MCP 是无状态工具调用，多轮对话需要会话编排，且 specflow 的参与者是**人** |
| ④ 复用引擎 | 把平台内部能力（面试官、解析器、制造器）当 API 给外部系统调用 | ☆ 不值得：这些是带闸门与人参与的内部流程，剥离人之后价值与风险倒挂 |

### 2.2 三维度评分

每个场景按三维度评估：**对外价值**（外部消费者是谁、频率多高）、**闸门风险**（开放后是否可能稀释铁律）、**远期适配度**（是否属于远期规划的主体能力，还是早期遗留）。

### 2.3 遗留处置原则

现有 24 工具不是「开放面」而是「内部工具面」——对外开放面应**按远期场景重新设计**，从内部工具中裁剪映射，而不是把 24 工具整体暴露。旧工具分三类处置：直接映射（spec_reader 等只读类）、改造后映射（run_scenario 加范围限制与配额）、永不映射（promote_draft、edit_dependency 等）。

## 3. 需求面试专题（M02/M03/M04/M05）

### 3.1 为什么「面试过程」不值得也不应该 MCP 化

需求面试（IV-xxx）的本质：**面试官 Agent 围绕议题对人（产品经理）做结构化追问，决策由人落锤**。四个硬约束决定它不适合对外 MCP：

1. **形态错配**：MCP 是单次、无状态的工具调用；面试是多轮、有状态、依赖会话上下文的对话。specflow 已有正确承载——AgentChat + purpose 锁定的会话（M01），外部要参与面试的正确方式是**进工作台**，不是调工具。
2. **参与者错配**：被面试者是人。P0 提问必须得到人的回答才产生 D-xxx 决策（铁律 1：Agent 只建议、人拍板）。让外部 Agent 代替人回答面试问题，等于让 Agent 拍板——直接击穿铁律 1，一票否决。
3. **上下文错配**：面试官的提问质量依赖材料包解析 + 基线锚点 + 未闭环 SPQ + 上轮报告装配的 info_pack（M02/M03），这套装配是会话级内部上下文，无法压缩成一次工具调用的入参。
4. **闸门错配**：P0 清零门禁、五维评分确认、三闸冻结全部要求人在回路（M04/M05）。把面试引擎 API 化却不附带人，产出的是没有决策效力的空壳 spec。

**结论：面试过程（IV 会话、提问生成、决策落锤、五维确认）永不进入对外 MCP 面——这不是技术保守，是该能力的价值本身就是「Agent 辅助人做决策」，抽掉人就没有价值。**

### 3.2 值得开放的三个面（「产物全开放、入口半开放」）

**A. 面试产物 · L0 只读（🟢 强烈值得，G2）**——这是外部世界对 specflow 的真实需求：

| 对外工具（新建，挂在 specflow_refs 模块） | 内容 | 头号消费者 |
|---|---|---|
| `get_frozen_spec` | 冻结 spec.md：FR 锚点 + SHALL + [delta] 标记 | **编码 Agent**——写代码前读「合同」（旧分析 S1 旗舰场景的 specflow 升级版：测试侧 spec 之外，新增需求侧冻结产物） |
| `get_proposal` | proposal 四段式（为什么做/做什么/不做什么/验收口径） | 研发、QA、跨团队——理解需求意图 |
| `query_decisions` | D-xxx 决策台账查询（P0/P1/P2、状态、增补链） | 编码 Agent 查「为什么这么定」；审计查决策依据 |
| `get_interview_status` | IV-xxx 进度、P0 清零状态、五维评分、冻结门禁状态 | PM/QA 看板、发布门禁（S4 场景的需求侧数据源） |
| `get_delta_contract` | delta 三段式 + manifest + 契约版本期望 | 编码 Agent 判断改动落在哪个 delta、契约是否受影响 |

价值论证：远期规划上线后，spec 的**生产地**从纯测试侧扩展到需求侧——冻结 spec 是编码 Agent、研发、QA、审计四方都需要的单一事实源；读面零闸门风险（conformance 纯读哲学的对外延伸）；这与「编码 Agent 产出入链被治理」互补战略完全同向。

**B. 面试入口 · L1 草稿态（🟡 受限开放，G3 评估）**：

| 工具 | 内容 | 约束 |
|---|---|---|
| `submit_interview_topic` | 外部系统（禅道、PM 工具、研发）提交面试议题：标题 + 来源链接 + 相关材料引用 | 一律落**草稿态议题池**，人开标才成为 IV-xxx；不允许指定优先级、不允许跳过材料包装配；调用配额限制 |

价值论证：需求来源天然分布在多个系统（禅道故事、业务方邮件、研发技术债），给一个标准化的「议题投递口」比让人肉转述更不易丢需求；草稿态 + 人开标保证铁律 1 不被稀释。

**C. 面试过程 · 🔴 不开放**（见 3.1，含：面试官提问生成、材料包上传解析、决策落锤 resolve/amend、五维评分确认、冻结导出——这些连 L1 都不进，部分按「外部写不进 MCP」通则连内部 MCP 都不暴露）。

### 3.3 材料包（M03）为何不开放

材料含会议纪要、访谈记录、PRD 原文——业务敏感浓度最高（干部盘点规则、绩效逻辑），上传与解析是工作台内人的选型行为（产品选型入包）；外部经 MCP 投递原始材料 = 绕过密级审查与人选型，双重不可接受。外部只需引用编号（材料包条目 MAT-xxx 作为议题附件引用），不传输原文。

| 模块 | 场景 | 判断 | 理由 |
|---|---|---|---|

| M07 覆盖缺口 | 缺口泳道/测试债查询 | 🟢 L0 | 研发自查与质量透明（S3 场景）；「生成下一批」不开放（触发的是内部生成流程） |

| M06 禅道集成 | 禅道 story/bug 写 | 🔴 | 「外部写不进 MCP」通则，内外部一视同仁 |
| M08 DAG 批次 | 计划/批次/DAG 校验状态查询 | 🟢 L0 | 发布门禁（S4）与研发可见性 |

| M08 DAG 批次 | 测试数据制造 | 🔴 | 带闸门的内部 Agent 流程（数据校验器闸门），且数据制造涉及被测系统资源调度 |

**汇总**：🟢 8 组（全部只读）、🟡 3 组（草稿/受限）、🔴 6 组。开放面的**主体是远期新增能力**（specflow 产物、血缘、图谱、禅道反查），旧 24 工具能直接映射的只有 spec_reader / registry_query / read_run_report / check_dag 这一小撮——**印证了你的判断：现有 MCP server 与远期规划已不适配，对外开放面需要按上表重建而非平移。**

## 5. 对外开放面的目标形态

新建对外专用 MCP 模块（与内部 `mcp_server` 同 server、独立工具命名空间，G2 随远程化落地）：

```
mcp_server/tools/open/                    # 对外开放面（独立挂载、独立白名单）
├── specflow_refs.py   # get_frozen_spec / get_proposal / query_decisions
│                      # get_interview_status / get_delta_contract（新建，M05/M04/M06 数据）
├── quality_query.py   # 覆盖缺口 / 测试债 / 计划与批次状态（M07/M08 读面）
├── lineage_query.py   # Q1/Q2 trace（M10）+ 图谱查询（M11）
├── refs_query.py      # ZT 反查（M06 sf_external_refs）
└── intake.py          # submit_interview_topic（L1，G3）/ report_vulnerability（改造映射）
```

治理纪律（承前两份分析，不重复展开）：全量 `side_effect` 分级、per-client 白名单三层交集、OBO 身份到工号、统一审计、L0 面纯读运行时强制；旧 24 工具保持内部 stdio 面不变，对外只经 `open/` 命名空间暴露裁剪后的子集与新工具。

## 6. 分期与触发条件

| 阶段 | 内容 |
|---|---|
| **G2** | L0 只读面 8 组上线（含 specflow 产物查询 specflow_refs）——这是对外 MCP 的真正起点，随远程化（Streamable HTTP + SSO）一起落地 |
| **G3** | L1 两组评估开放：submit_interview_topic（议题投递口）、run_scenario 受限子集；归因建议提交改造映射 |
| 储备项 | 生态开放（注册 MCP Registry、对外文档）——触发条件不变：外部接入需求 + 内部跑稳一季度 |

**需求面试部分的最终口径**：G2 先开产物五件套（get_frozen_spec / get_proposal / query_decisions / get_interview_status / get_delta_contract），G3 评估议题投递口，面试过程永不在路线图上。

---

## 7. 一句话回答

**值得对外提供的不是「面试能力」而是「面试结果」**：需求面试的过程（多轮人机对话 + 人拍板）与 MCP 形态天然不兼容，永不应开放；但面试产出的冻结 spec、决策台账、评分与进度，是编码 Agent、研发、QA、审计四方都需要的质量事实源，应作为对外 MCP 的 L0 主体在 G2 落地——连同血缘、图谱、禅道反查一起，按远期规划重建开放面，而非平移早期的 24 工具。
