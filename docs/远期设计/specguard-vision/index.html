汇报提示 · S1这一屏回答一个问题：为什么要从测试工具扩张成全链路平台——因为需求没说清，下游全都白忙。中间这个大循环是核心叙事：测试发现的问题，恰好是下一轮需求讨论的素材，把需求讨论搬进来之后，这个环才真正闭合。页面底部是四句「角色话术」——被问到为什么不用 Codex / Claude Code时，领导、产品、测试、研发各有一句答案；研发那句的重点是：我们给编码 Agent 供高质量上下文。
VALUE OVERVIEW · 为什么做
一个之前闭不上的环，
现在闭上了
过去 SpecGuard 只管「测」这一环，前提是上游需求已经写清定稿——但这个前提没人保证。
现在把需求讨论也搬进来：需求先谈清 → 再开发 → 再测试 → 问题自动回到下次需求讨论，环闭上了。
五环大循环 · 鼠标悬停任意一环，看它在价值链里的作用
PAIN POINT · 现状痛点

需求没说清，下游全白忙

每个用例都能追到需求条目、覆盖缺口有矩阵、需求一变测试计划自动跟进——这些能力有个共同前提：需求写得清楚、定了稿。需求一含糊，用例生成、缺口分析全都跟着错。

ARCHITECTURE · 各管各的

需求侧、测试侧，两套体系不混放

两边各自成体系、过程产物互不混放。只交接两样定稿产物：需求基线（需求侧写、测试侧读）和变更清单（需求侧出、测试侧一键生成测试计划）。规范标准两边共用。

CORE VALUE · 问题回桌

测试发现的问题，自动回到需求桌上

没闭环的需求疑问和执行报告摘要，自动装进下轮需求讨论的材料包，直接成为提问素材——环就是这样闭上的，这是整个体系的核心价值。

WHY SPECGUARD

为什么不是 Codex / Claude Code？——四个角色，各一句话

通用 AI 编程工具 ≠ 工程质量资产平台
对领导

Codex / Claude Code 是让 AI 帮人写代码的通用工具，用完即走；SpecGuard 把「需求→验证→反馈」整条质量链沉淀为组织资产——决策台账、冻结 spec、血缘链可追溯、可审计，不随人流失。

对产品

Codex / Claude Code 面向程序员写代码，没人管需求质量；SpecGuard 给产品经理一个 AI 面试官——把模糊想法盘问成 P0 清零、锚点规范、三方冻结的 spec，「需求没说清」不再是下游带病工作的源头。

对测试

Codex / Claude Code 也能生成用例，但它不认识你的需求条目、不记得上轮执行发现的疑问；SpecGuard 的用例从定稿需求里长出来、来源不断链、执行结果回到下轮需求讨论——不是"生成"出来的，是从契约里"长"出来的。

对研发

Codex / Claude Code 写得快，但它不知道你的需求最终怎么定的——接需求、修 BUG 时，SpecGuard 给出带版本号的「需求上下文包」：需求定论、接口约定、验收标准、相关测试场景，你和你的编码 Agent 读到的是同一份——高质量上下文，是高质量代码的前提。
