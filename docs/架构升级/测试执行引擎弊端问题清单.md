### ENG-BUG-002 契约版本门禁偏弱
- **类别**：契约安全 / 回归
- **严重度**：中高　**优先级**：P0
- **证据**：
  1. **pin 可选**：`versioning.match_expectation`（`versioning.py:57-58`）`expected` 为空直接 `MATCH` → `depends_on` 不写 version 时永不报漂移。
  2. **指纹漏断言**：`contract_fingerprint`（`versioning.py:96-108`）只对 `produces/saves/covers` 指纹，**不含 `verify` 断言逻辑、teardown、flow 结构** → 改断言预期（如 `eq:null → eq:0`）指纹不变 → T6 不报 ERROR。
  3. **传递依赖不校验**：`_check_dep_versions` 仅在 `run_with_deps`（`scenario_runner.py:1070`）调用；而 `_acquire_instance`（`scenario_runner.py:989`）直接调 `run_scenario` 绕过它 → **依赖链深层（非根目标直接依赖）的契约漂移完全不被检查**。
  4. ~~**漂移非 FAIL**~~ → **核对更正，见下**。
- **核对更正（第 ④ 条因果颠倒，2026-08-20）**：
  - 清单初稿称"DRIFT/ORPHANED 是非 FAIL 状态 → 只在 FAIL 时失败的 CI 门禁会漏掉契约漂移；仅 strict_deps 能拦"。**pytest 路径下事实相反**：`test_scenarios.py:74` 判定 `verdict != PASS → pytest.fail`，DRIFT/ORPHANED **默认就失败**；strict_deps 退化为 BLOCKED 后走 `test_scenarios.py:72-73` 的 `pytest.skip`——**开 strict 反而让 CI 放过漂移**。`release_check.py:42-49` 发布门禁无论 strict 与否都把 DRIFT/ORPHANED 计为 blocker。

- **影响**：断言逻辑被悄悄改写无法触发版本门禁；下游传递依赖版本失配无人知晓（且传递 orphan 直接崩溃，见 ENG-BUG-010）；漂移在 pytest 下失败但消息为空。

### ENG-BUG-003 无 HTTP 重试 / 无场景级超时
- **类别**：稳定性
- **严重度**：中　**优先级**：P1
- **证据**：
  - `http_client.request` 仅对 401 做 token 刷新重试（`http_client.py:97-100`）；对 5xx / 网络抖动 / 超时**无任何 retry/backoff**（仅 `token_provider.py:102-129` 有 3 次指数退避）。
  - 单次 HTTP 有 timeout（默认 30s），但**场景级无 wall-clock 看门狗**：`step_python` 内 `while True` 会永久挂起整个 run；`poll` 的 `time.sleep` 无可取消。
- **核对补充**：workbench runner 层已有 **run 级看门狗**（T-118，`runner.py:481-526`，settings KV `run_timeout_sec` 优先、回退环境变量 `SG_RUN_TIMEOUT`，**默认 0=禁用**）。引擎级场景超时确实没有，本条成立；修复时应注明与 T-118 的分工（引擎软看门狗负责"场景内可中断点"，T-118 负责"进程级强杀"）。
- **影响**：SIT 网关偶发 500/503 → 响应照常捕获 → 断言失败 → 假 FAIL；单个坏场景可拖垮整轮。
- **建议修复**：① 新增可配置重试（次数 + 退避，仅对幂等 GET/可标 `idempotent` 的请求）；② 新增场景级软看门狗（步骤边界检查累计耗时，超阈值抛 `ScenarioTimeout` 归 `CAT_ENV` 并附"超时"提示；exec 死循环不可硬中断，依赖 T-118 兜底）。
